## 二、评审提出的四个问题（已全部修复）

### 1. 未来生效的基准会提前参与历史录入

新增 `baselineAtTime(baselines, pointId, sampleTime)`：只选取 `effectiveFrom ≤ 采样时间` 的版本，取其中生效时间最晚的一版。
录入弹窗的实时试算、预警标准页的单条试算、演示脚本核对、保存记录后的正式判定，全部改为按采样时间取基准 —— 四条路径收敛到 `stores/assessment.ts` 的 `assessPoint()` 一个入口。

录入弹窗现在会明确显示"基准与规则版本均按**采样时间**选取：某时刻生效的是 v2。未来生效的基准不会参与本次录入。"

### 2. 规则版本覆盖式编辑，历史解释无法成立

规则改为**版本行**模型：每次保存规则生成新的版本行（`V1.0 → V1.1` 自动递增），旧版本行原样保留，不再覆盖。
判定按采样时间选取当时生效的版本；事件的每条证据都带判定快照（规则编号、版本、阈值、触发值、基准值、判定依据）。

因此"为什么当时是橙色"可以事后追溯：即使后来把黄色阈值从 0.10 调到 0.05，那条历史证据仍显示它当时命中的是 V1.0 的 0.10 阈值。

### 3. 演示脚本表两处展示矛盾

表格拆成两列：「实算数据状态」是按当前规则跑出来的结果，「允许操作」是状态对应的下一步 —— 两者不是同一个维度，不再混在一起。
标准表与实算结果并列显示，页面上直接说明"右侧一列才是系统实际判定"，并解释了为什么维修后单独一条 0.54 mm 不构成恢复待确认（规则要求连续 3 条）。
原文档中"16 条脚本全部对应"的表述已一并更正为按列分开说明。

修正过程中还发现两处数据问题，一并处理：
- **倾角基准与标准不符**：示例里倾角基准是 X 0.20° / Y −0.10°，而项目组标准写的是 X 0.00° / Y 0.00°，
  导致倾角脚本第一行 0.04° 被判成黄色（相对 0.20 基准变化 −0.16）。已把倾角基准改为 0.00° / 0.00°，示例记录改到正常区间。
- **脚本核对混入了现场记录**：脚本推演原本会把数据库里的真实记录算进历史，结果不可复现。
  已加 `sequenceOnly` 开关，脚本核对只用自身序列。

改完后三段脚本（裂缝 8 条、倾角 4 条、振动 4 条）的实算结果全部与标准预期对应。

### 4. "生成关注提醒/生成复查任务"只是规则说明

规则阈值表的列名改为「命中后预期动作」，并在表前说明：
"黄色与橙色以上等级会由系统自动生成或升级预警事件；处理中、待验收等处置动作属 V0.3 与 V1.0。"

补充说明：本次已把"自动生成或升级预警事件"这一项**做成真实动作**，不再是说明文字；只有处置类动作（派单、维修、验收）仍属后续版本。

## 二之五、V0.2 收尾：趋势图历史规则修复、CSV 批量导入与规模合规

### 1. 趋势图按采样时间取规则版本

每条记录按自己的采样时间取当时生效的规则版本判定，阈值线与基准线按"规则换版时间 ∪ 基准换版时间"分段绘制，
页脚写明"阈值线 = 该时段生效基准 + 该时段生效规则阈值"，并标注出现过的规则版本（如 V1.0 → V1.1）。

**实机发现并修复一个真实缺陷：阈值线取到了同表内其他指标的规则。**

- 现象：裂缝测点图上的三条阈值线画在 0.05 / 0.10 / 0.20，而不是"基准 0.50 + 0.10 / 0.20 / 0.30"的 0.60 / 0.70 / 0.80。
- 原因：`buildRuleSegments()` 只按"生效时间不晚于该段起点"筛选，没有按"这条规则是否适用于本测点"过滤。
  规则表里四类指标同表存放、且同在 2026-08-01 生效，取"最后一条生效版本"时命中了同一天生效的振动规则
  （其阈值恰好是 0.05 / 0.10 / 0.20），于是把振动阈值画到了裂缝图上。
- 修复：把适用范围判断抽成 `ruleAppliesTo(rule, point)`，判定用的 `ruleForPoint()` 与图表用的
  `buildRuleSegments()` 共用同一口径；新增 `rulesForPoint()` 返回该测点适用的全部版本。
- 回归测试 2 条：同表内其他指标的规则不参与本测点阈值线；楼栋范围不覆盖本测点的规则不参与分段。
- 修复前后实机读数（读取页面 SVG 实际坐标并按纵轴刻度反算）：

| 阈值线 | 修复前 | 修复后 |
| --- | --- | --- |
| 黄色 | 0.05 | 0.60（换版后那一小段抬到 0.62） |
| 橙色 | 0.10 | 0.70 |
| 红色 | 0.20 | 0.80 |

基准 0.50 mm；裂缝规则阈值为相对基准 +0.10 / +0.20 / +0.30 mm；V1.1 把黄色阈值改为 +0.12。

### 2. CSV 批量导入

两个入口共用一套解析：**上传 CSV 文件**与**粘贴文本**。解析后先出预览，逐行标注「通过 / 警告 / 错误」与原因，
底部给「确认导入 N 行」按钮（N = 通过数 + 警告数），错误行只在预览里提示、不写入正式数据。

逐行校验覆盖六类问题，全部复用录入校验 `checkReading()`，因此导入与手工录入的标准完全一致：

| 类别 | 判定 | 提示示例 |
| --- | --- | --- |
| 表头 | 缺「测点编号」或「采样时间」→ 整份文件不可导入 | 表头缺少必需列 |
| 测点 | 编号不在档案中 | 测点编号 B99-X 在档案中不存在 |
| 指标 | 人工检查点不接受数值导入 | 该点位是人工检查点，不接受数值导入 |
| 时间 | 无法解析、与已有记录同分钟重复 | 同一点位该分钟已有记录 R20260905-001，请改用修订并保存原值，或调整采样时间 |
| 数值 | 缺必填项（不按零处理）、超出合理区间 | 裂缝宽度为必填，缺项不按零处理 |
| 单位 | 不属于该指标 | 单位「g」不属于该指标，应为 mm |

单位留空不算错误，按指标默认单位处理并在预览里说明（"单位留空，按指标默认单位 mm 处理"）。
填了本指标用不到的列会提示"已忽略"，不会把角度写进裂缝记录。错误行 `payload` 为 `null`，写入环节拿不到它。

**确认导入复用现有录入路径**：`stores/writes/importWrites.ts` 只做一件事 —— 对每一条可导入行调用
`records.addRecord()`，也就是手工录入用的同一个函数。因此基准快照、规则判定、事件去重升级与通知完全一致，
没有第二套导入判定。审计日志留一条 `import` 记录（"CSV 批量导入：写入 N 条，跳过错误行 M 条"）。

| --- | --- | --- |
| 任务生成幂等 | `planTasksFor()` 按「计划 + 执行时刻」去重，循环内再查一次批次键 | 首次点"生成今日任务"新增 1 条；再点提示"今日任务已是最新…不会重复建单"，任务数仍为 1 |

### 3. 两个 P0 修正（评审提出）

**（1）任务生成的幂等从"顺序"升级到"并发"。** 原实现用内存里的任务列表与本次循环的批次键去重，
连续点击能跳过，但快速双击时两个异步调用都可能看到"尚不存在"而各写一条。现在把唯一性落到数据库：

- 任务主键就是业务键 `taskKeyOf(planId, plannedAt)`（形如 `plan_x@2026-09-20T01:00:00.000Z`），
  同一计划同一执行时刻天然唯一；
- 生成在**一个读写事务**里完成：事务内重新查已有主键，不存在才 `add()`，撞键由 IndexedDB 抛错拦截；
- 任务序号也在同一事务里按当时已有的编号计算，并发下不会算出同号；
- `planTasksFor()` 的责任收窄为"今天理论上应做哪些任务"，不再判断"是否已生成"——
  那个判断必须由数据库回答。

新增并发测试（用 `fake-indexeddb` 跑真实 IndexedDB 行为，含 7 项）：
`Promise.all([generateFor(day), generateFor(day)])` 后任务表只有一条，两次调用的
`created + skipped` 合计为 2；两个计划并发生成时任务编号不重复。

**（2）任务保存不可变的计划快照，范围与归属不再被计划修改追溯改写。**

`InspectionTask.planSnapshot = { planCode, planName, executorRole, buildingId, floorIds, pointIds, checklist }`，
生成任务时写入。原实现有两个真实缺陷：多楼层计划只写了 `floorIds[0]`（跨楼层任务丢范围，打卡、地图定位、
问题上报都可能显示错位置）；"我的任务"实时读当前计划的 `executorRole`（管理人员改一次执行角色，
历史任务就被重新分配给新角色）。现在任务卡、我的任务、以及后续的打卡与问题提交一律读快照。

新增三类测试：跨两层的计划范围完整保留；计划改执行角色后旧任务仍归原角色；计划改必查点后旧任务保留原检查点、
新任务才用新范围（另含一条"计划被删掉任务仍可读快照"）。

### 4. 顺带修正的两个口径问题

- **截止时刻用当日结束，不用计划时刻**。原实现 `dueAt = plannedAt`，上午生成的任务下午就显示"逾期未检"。现改为当日 23:59:59，任务卡同时显示"计划时刻"与"当日截止"。
- **任务卡的时间显示取本地时间**。原实现直接截 ISO 字符串，09:00（本地）被显示成 01:00（UTC）。改用统一的 `formatDateTime()`。
- 「我的任务」空着时看不出原因，加了一行"当前各角色任务数"，换身份前先知道任务在谁手上。

### 1. 我把"到点"与"检查完成"拆成了两个状态（评审确认后实施）

### 7. 第四轮修正（事务原子性、入口收窄与草稿归属）

**（1）P0：问题创建 + 任务关联改为单个 IndexedDB 事务。** 原实现先写问题、再写任务关联，
中间失败会留下"问题已建但任务没关联"的半成品：页面重试只能靠"同一次提交"的 10 分钟时间窗去重，
窗口一过就再建一条，而任务里始终没有关联。现在新增 `db/inspection/disposal.ts` 的 `commitDisposal()`，
把**问题行、更新后的任务、两条操作日志**放进同一个事务提交 —— 要么都成立，要么一条都不落库。
测试两条：① 一次提交后问题 +1、日志 +2、任务结果已关联，重试复用同一条且日志不再增加；
② 人为让事务内写入失败（替换 `db.audits.bulkPut` 抛错）→ 问题、任务、日志三者都保持原样，恢复后重试只生成一条问题。
实机验证：提交前后对比 `问题 +1 / 日志 +2 / 任务结果 linked: false → true`。

**（2）P1：问题写入入口按来源收窄。** `submitIssue()` 不再对外暴露（改为内部的 `buildIssueRow()` +
`persist()`），对外只有三个入口：

| 入口 | 谁可以调 | 约束 |
| --- | --- | --- |
| `tasks.reportInspectionIssue(taskId, pointId, draft)` | 该任务的执行角色 | 先 `guardPoint()`，再事务提交问题 + 任务关联 |
| `issues.reportManualIssue(draft)` | 现场任何身份 | 人工上报不属于某个任务，`taskId` 为空 |
| `issues.createIssueFromEvent(draft)` | 仅学校安全管理人员 | 预警转单，来源 `sensor` |

边界说明：`reportInspectionIssue` **只覆盖巡检发现**；人工上报与预警转单没有 taskId，
强行塞进任务入口会编造一个不存在的任务，因此各自独立入口（这两条的页面在第四步接）。
顺带修掉一处噪音：重复关联同一问题时不再写库、不再写日志（避免"重试产生伪造的新增记录"）。

**（3）P1：照片关联返回值强制校验。** `attachPhotos()` 返回 `null`（问题在本机数据里找不到）时，
页面按失败处理：保留草稿、提示"照片关联失败…草稿已保留"，不再提示成功。
`uploadDrafts()` 里同样把 `null` 当失败并中断，返回"附件已保存但关联到问题失败"。

**（4）P1：`IssueForm` 的照片草稿真正由父组件持有。** 改用 `defineModel<PhotoDraft[]>('photos')`，
`TaskDetail` 的 `issueDrafts` 成为唯一来源 —— 切换点位或关掉表单后草稿不再丢失（"失败保留草稿可重试"才成立）。

### 8. 第五轮修正（并发唯一性、写入入口收束与事务覆盖）

**（1）P0：并发提交同一巡检问题只生成一条 —— 用"同一提交标识 = 同一主键"实现，未加唯一索引。**

> **注：本小节第一版讨论的是 FNV-1a 哈希主键，该方案已废弃**（哈希有碰撞面，一旦碰撞会把两次不同提交
> 静默并成一条）。当前实现是**完整提交标识的 base64url 编码作主键**，见下一节"第六轮收口"。
> 保留这段是为了记录"为什么不做唯一索引"，不要照着这里的哈希方案去改代码。

评审建议升到 v5 给 `issues` 加 `&submissionKey`、`&issueNo` 唯一索引。**这一条我没有照做**，理由如下：

- 唯一索引要在版本升级时建立，**旧库若已有重复行，升级会直接失败**（IndexedDB 在建唯一索引时校验既有数据），
  用户会打不开数据库；真要做，得拆成"v5 建普通索引 + 数据去重、v6 再建唯一索引"两步，风险与工作量都不小。
- 同一份保证可以用更低风险的机制拿到：**提交标识 → 确定性主键**（`issueIdOf()`，FNV-1a 哈希，和任务表用
  `计划ID@执行时刻` 做主键是同一套办法）。并发双击时两个请求算出同一个主键，第二个 `add()` 撞主键 →
  识别为"已存在"并复用；`issues` 表的主键本身就是唯一约束。
- **编号在事务内分配**：IndexedDB 对同一 store 的读写事务是串行的，第二个事务读到的是第一个提交后的最大值，
  因此并发下不会算出同一个编号（这也是评审要求的"事务内读当日最大值"）。

测试与实测都覆盖了评审列的两条必测：
`Promise.all` 并发相同提交 → **1 条问题、1 条任务关联、2 条日志**；并发不同异常类型 → **2 条不同编号的问题**。
实机双击（同一 tick 连点两次"提交问题"）→ 问题 +1（主键 `iss_9e1d2898`）、日志 +2、任务关联 1 条。

> 如果你仍希望把唯一索引作为"数据库层的第二道锁"，我按两步迁升级来做（v5 去重 + v6 唯一索引），
> 但那属于库结构变更，需要单独一轮验证。

**（2）P1：人工上报与预警转单也改为单事务。** 原先 `persist()` 先写问题、再写日志，日志失败会留下没有审计记录的问题。
现在两条入口都走 `createIssueAtomic()`：**问题行与日志在同一个事务里提交**。

**（3）P1：底层方法不再对外暴露。** 问题行构造（`planIssueRow`）与事务提交（`createIssueAtomic`）移入
`db/inspection/issueWrites.ts`；Issue Store 的对外接口只剩 `reportManualIssue()`、`createIssueFromEvent()`、
`attachPhotos()` 与各类查询，页面拼不出绕过受控入口的写入路径。

**（4）并发还揪出两处"读内存快照"的隐患**（真机与测试各抓到一次）：
`loadWriteContext()` 原来只在缓存未命中时回查数据库，而并发下缓存**命中但已过期** —— 结果把"已经建好关联的任务"
判成没关联，多写一条日志。现在任务与问题一律**以数据库为准**读取。这类"缓存命中但过期"的错误比"缓存未命中"隐蔽得多。

### 9. 第六轮收口（并发唯一性闭合）与一处口径冲突

**（1）主键改用完整提交标识编码，不做哈希。** 上一版用 FNV-1a 32 位哈希做主键，理论上会碰撞 ——
一旦两条不同的提交算出同一主键，后一条会被当成"已存在"而**静默复用**，两次不同的现场发现被并成一条。
现在主键是 `iss_` + 提交标识的 base64url 编码（`TextEncoder` + base64，浏览器与测试环境都可用），
**不存在碰撞面**；同时在 `createIssueAtomic()` 里保留一道显式防线：主键命中时核对 `submissionKey`，
不一致直接抛"问题主键冲突"，绝不静默复用。

**（2）问题校验一律读库。** `linkIssueToPoint()` 与 `completePointCheck()` 原先"缓存优先、未命中才读库"，
缓存里那条可能已关闭、已改归属或被删除，拿它当处置依据会把错的关联写进去。现在两处都是无条件 `db.issues.get()`。

**（3）到点、完成检查、关联既有问题统一为"任务 + 日志"单事务。** 新增 `commitTaskWrite()`，
`write()` 不再先落任务再写日志 —— 日志失败会留下**没有留痕**的到点或检查完成记录，
而这套系统的价值恰恰在于"每件事都能倒查"。

### 12. 工单闭环：从"审核标签"变成真实工单（评审最优先项）

**（1）审核转维修时原子建单。** `to_repair` 不再只改问题状态：审核通过时**在同一事务里**创建一张"待派工"工单
（`commitIssueWithWorkOrder()`：问题 + 工单 + 两条日志一起提交）。问题状态与工单**同生共死** ——
要么问题进入"处理中"且工单存在，要么两者都不落库，不会出现"显示维修中却没有工单"的假状态。
工单编号 `WO-YYYYMMDD-001`，来源按问题来源记为"人工问题转单"或"预警转单"。
测试：建单成功时问题与工单同时成立（单号格式、来源、`workOrderIds` 回填）；**人为让工单表写入失败 →
问题状态与 `workOrderIds` 都不变**，恢复后重试才一起成立。

**（2）工单闭环全链路（派工 → 接单 → 完工 → 验收）。**
- 派工（仅安全管理人员）：指定维修人与期限；核心判定补了"必须指定维修人"（不指定人的"已派工"现场没人接）；
- 接单与提交完工（维修人员或物业值班）：核心判定补了角色限制 —— 界面隐藏按钮不算权限，仓储同样拦；
- 完工：措施必填、材料选填、完工照片随备份入库（附件带 `workOrderId`，不留游离数据）；
- 验收：通过或退回（退回必写原因），退回后可继续处理；
- **验收通过后问题只进入"待复查"，不自动关闭**（方案 §3），页面写明"事件关闭还需要连续 3 条恢复复测与处置依据"。

**实机验证（完整链路一次走通）**：人工上报"探头松动" → 审核「转维修工单（设备故障）」自动生成
`WO-20260921-001`（待派工）→ 派工给维修人员并设期限 → 接单（状态处理中）→ 填措施与材料提交待验收 →
安全管理人员验收通过 → **问题状态变为"待复查"、时间线出现"进入待复查"**，工单时间线 5 条、验收记录 1 条。
维修身份在"待派工"状态下看不到派工按钮、也看不到审核区（页面与仓储口径一致）。

**（3）实测中抓到的两个真缺陷。**
- **提交待验收永远失败**：仓储先把 payload 交给 core 判定、再合并字段，而 core 校验的是**库里那份旧工单**的
  维修措施 —— 措施恰恰是这一次才填的，于是必然报"必须填写维修措施"。改为**先把提交内容并入候选状态再判定**，
  并补了回归测试。
- **照片预挂载多此一举且有害**：完工照片入库时已带 `workOrderId`（归属已定），我却额外调了一次"以原状态流转"

### 2. 三个 P0 与两个 P1 改了什么

**P0-1 工单编号入事务。** 原来 `createForIssue()` 在事务外读一遍工单表算出 `WO-日期-序号`，再交给写事务；
两条并发转维修会算出同一个号，而工单主键是随机 ID，数据库不拦重复编号。现在改成：`buildForIssue()` 只构造行
（`orderNo` 留空），编号在 `commitIssueWithWorkOrder()` 的读写事务里分配 —— IndexedDB 对同一对象仓库的
读写事务串行执行，第二个事务必然读到第一个提交后的最大值。编号分配统一收进 `db/inspection/numbering.ts`，
问题编号也改用同一个入口（原来 `issueWrites.ts` 与 `numbering.ts` 各有一份"当日日期键"的实现，已合并）。

**P0-2 验收权限。** `core/inspection/workOrderFlow.ts` 的 `advance()` 原来只拦派工、接单与提交完工，
`verified` / `returned` 靠页面 `v-if` 隐藏按钮。现在核心状态机显式要求 `byRole === 'safety'`，任何调用方
（页面、脚本、未来新增入口）都绕不过去。

### 3. P1 三项

- **规则迁移进事务**：原来 `deleteRules(staleIds)` 与 `putRules(rows)` 是两次独立事务，中间刷新或崩溃就
  **永久丢掉规则**（迁的正是旧库唯一的规则副本）。新增 `replaceRules()` 把删除与写入包进一个事务。
- **导入备份的原子性**：`SettingsView` 在调 `restoreDataset()` 前先手动清空全表，而 `writeDataset` 内部
  本来就是"清空 + 写入"一个事务 —— 外面这一清把事务撕成两半，清空已提交、写入未开始时失败就留下一个空库。
  删掉外层清空即可（导入前的安全备份仍照常自动下载）。
- **`RecordDialog` 拆分**：`fields` computed 85 行超硬性指标，拆成 `readingFields()`（读数与测点）
  与 `metaFields()`（单位/时间/窗口/设备/来源/质量/备注/修订原因），computed 本身变成一行。

### 4. P2/P3 四项

- `markPresented` 由"逐条 put"改为一次 `putNotifications`（逐条写中途失败会留下半已展示半未展示的通知）。

### 5. 我选择不修的项与理由

1. **CSV 导入的 O(n²)（逐条 `addRecord` 每条全量 reload）** —— 不修。
   `addRecord` 里的 `reload()` 是**承重的**：记录编号 `nextRecordNo(dayKey, records.value)` 靠它读当日最大值，
   跳过 reload 会让同一批 CSV 里的多行算出同一个 `recordNo`。要改为"一次 reload + 本地维护已用编号"，
   等于动编号口径，必须配套一批编号测试 —— 这是 P2 性能项，而演示的 CSV 只有几十行，
   不值得在答辩前动这条承重路径。**结论：留作已知项，真要做批量导入（上千行）时再改。**
2. **模板里重复排序/重复取值**（楼层表每行调带 sort 的 `pointsOfFloor`、`MonitorView` 同格调三次 `levelOfRow`）——
   在 4 栋楼 / 8 测点的演示数据下开销可忽略，改动会碰到渲染结构，收益为零，**不修**。
3. **路由懒加载、键盘可达性、SVG 固定 id、`Date.now()` 不随时间的非响应式** —— 都是 P2/P3 的体验与
   规模项，跟本轮"数据正确性"不是一条线，**未动**；其中 `Date.now()` 那条（逾期/待办不随时间自动刷新）
   要引入定时器，属于设计决策，需要你先定"演示时要不要它实时滚动"。

### 2. 关闭的三道门

关闭现在是"三道门一起过"，任何一道不过都写不进去（判定都在仓储层，页面隐藏按钮不算权限）：

1. **权限与时机**（`core/event/plan.closeGuard`）：只有学校安全管理人员、只有"恢复待确认"状态；
   "恢复待确认"本身由判定引擎给出——连续 N 条有效记录低于「黄色阈值 × 恢复比例」，因此"连续复测"不是靠页面把关；
2. **处置依据**（`core/inspection/workOrderFlow.closeBasis`）：**当前事件关联工单已验收通过**；
   真实事件关闭始终按事件编号匹配，不能拿同测点旧事件的工单充当依据。只有调用方没有事件标识时，才允许按测点查询，
   或安全管理人员填写不少于 10 字的"无需维修"现场核查结论；
3. **依据必须落在库里**：关闭前的判定读的是数据库（`basisFromDb()`），不是页面缓存 —— 缓存可能"命中但已过期"，
   会把已在别处验收/关闭的状态判错。

关闭后**不改问题的状态**：问题仍停在"待复查"，它有自己的审核出口与关闭动作。
"验收 ≠ 问题关闭、事件关闭 ≠ 问题关闭"这条口径没有因为收尾而被破坏。

### 2. 照片原子提交：顺手解决了另外两件事

1. **不再二次压缩**：页面草稿（`PhotoDraft`）里存的**已经是压缩图**，而原来的写法把它重新包成 `File`
   再交给 `savePhoto()`，等于把压好的图又压一遍。现在新增 `buildDraftPhoto()` 直接由草稿构造附件行，
   压缩只发生在选图那一次。
2. **重试天然幂等**：附件主键改为 `att_` + 草稿标识（确定性主键，与问题的"提交标识→主键"同一套做法）。
   同一张草稿重复提交时算出同一个主键、事务里 `bulkPut` 覆盖同一行，不会留下两条一模一样的照片
   —— 照片重复上传这个问题之前在工单侧出过一次。

事务范围：非转维修出口走 `commitIssueLink`，转维修走 `commitIssueWithWorkOrder`，
两者的 `db.transaction` 作用域都加上了 `db.attachments`。

### 3. 未提交内容保护：三条出口一个闸

面板向上报 `dirty`（只有真的写了审核意见 / 传了照片 / 选了关联对象才算，出口与二级分类的默认值不算），
问题池把**切换问题、Esc、关闭按钮**（包括面板自己那个"关闭"）统一收进 `requestLeave()`：
有未提交内容时弹「存在未提交的审核内容」确认，选「继续填写」则留在原问题且内容不丢，选「放弃并离开」才离开。

## V0.3 第九项：预警触发提醒（V1-A 已完成）

- 手工实时录入在**新建事件或等级升级**后即时生成本机界面提醒；追加证据、恢复待确认、无事件不重复打扰。
- 红色事件用强提醒弹窗呈现；黄色、橙色进入顶栏“预警提醒”中心。弹窗明确说明“已生成站内通知”，不伪造短信、电话或应用推送送达。
- CSV 模拟设备导入仅显示一条批次汇总提醒；同一事件在同批内多次变化只按最终最高等级汇总，避免连续弹窗。
- 从提醒点击“查看并处置”会以路由参数深链到预警中心的对应详情，保留事件编号、证据、通知与处置入口。

**验证：** 手工录入裂缝宽度 `0.82 mm` 后生成红色事件 `E20260922-001`，强提醒显示测点、触发值 `0.32 mm` 与三名通知对象；点击后打开该事件详情。自动化测试新增 5 项，覆盖新建/升级、追加不提醒、红色强提醒、批次合并及历史补录/CSV 的非打断式规则。

V1 剩余和验收路径见 [V1.0冲刺计划.md](V1.0冲刺计划.md)。
