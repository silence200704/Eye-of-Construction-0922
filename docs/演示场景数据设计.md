> **实施状态：已实现并真机实测（2026-09-23）。** 实现落在
> `src/config/demoScenarios.ts`（场景目录与说明文案）、`src/config/demoScenarioSeries.ts`（序列数据）、

> 本文填的是**确切数据**（编号、数值、时间偏移、预期状态、调用入口），可直接照此实现。

## 0. 一句话

每个模块的「载入演示数据」= 调用该模块**已有的写入口**按固定剧本跑一遍，
结果由规则判定真实生成；重复点击按**已有业务键**幂等跳过；只更新本场景自己生成的数据；
每次载入写一条操作日志并把"本场景的业务对象编号"记进场景注册表，用于定位与高亮。

---

## 1. 硬约束（不可违反）

1. **不直接写结果**：`已关闭`/`已验收`/`已完成` 只能由状态机走到，禁止直接 `put` 结果行。
   每个步骤必须落到第 3 节列出的**写入口**。
2. **不新增库表**（推荐方案）：幂等靠既有业务键 + 一条场景登记记录，避免 Dexie v7→v8 迁移牵动 B1/B2/B3 验收。
3. **不覆盖手工数据**：场景只 `add`/`put` 自己键下的行；删除/更新只针对注册表里记录的编号。
4. **时间一律落在过去**：样本时间 ≤ 运行日 09:00，`addRecord` 会据此自动标"历史补录"，不伪装实时预警。
5. **保养异常不得产生结构预警**；温湿度不得产生结构红色预警；倾角不换算整栋倾斜结论（规则内已保证，演示脚本不得绕过）。
6. 规模：单文件 ≤450 行、函数 ≤80 行、参数 ≤5、每层目录 ≤8 个文件。

## 2. 场景注册表

**落地方式（推荐）**：不建新表。用 `archive.log()` 写一条登记记录，并**用确定性键反查**业务对象编号。

- 登记行：`action='import'`、`objectType='system'`、`objectId='demo:<场景键>'`、`objectLabel=<场景名>`、
  `summary='生成 N 条记录 / 1 个事件 / 3 条证据 / 2 次升级 / 7 条通知'`、`reason='演示场景；可重复点击，同键幂等'`。
- 编号靠反查（与现有 `runDemoScript` 返回 `eventNo` 的做法一致）：
  | 对象 | 反查方式 | 确定性键 |
  | --- | --- | --- |
  | 记录 | `points.records` 按 `(pointId, sampleTime)` | 采样时刻 |
  | 事件 | `events.openEventOf(pointId, ruleId)` | 未关闭的 `(pointId, ruleId)` |
  | 问题（事件转） | `issueIdOf('event:'+eventId)` | 事件 ID |
  | 问题（保养转） | `submissionKey='mt_'+taskId` | 任务 ID |
  | 问题（人工） | `submissionKey = source:place:anomalyType:时间桶` | 10 分钟桶 |
  | 工单 | `ordersOfIssue(issueId)[0]`（**转维修前必须判空**，`buildForIssue` 用随机主键） | 问题 ID |
  | 巡检/保养任务 | `taskKeyOf/maintenanceKeyOf(planId, plannedAt)` = `planId@plannedAt` | 主键本身 |
  | 附件 | `attachmentIdOf(draftId)` = `att_<draftId>` | 草稿 ID |

- 注册表只需在界面上回答三件事：**这个场景载过没有 / 载完要定位到哪条 / 重复点击会跳过什么**。

- **生成**：M2 已自动产出，本场景只做**确认与提醒**：`events.acknowledgeEvent(eventId)`（pending → handling），

### M5 点检巡检 —— 场景键 `inspection`

- **生成**（身份须为巡检人员，如"周老师（巡检班组）"/`inspector`）：
  1. `plans.savePlan(null, {...})` → 计划号 `PLAN-<今天>-001`：名称「3号教学楼二层日常巡检」、
     楼栋 B03、楼层 F0302（二层）、必查点 = B03-F2-CRACK01 / TILT01 / VIB01 / TH01（均在二层走廊）、
     执行角色 `inspector`、周期每日。
  2. `tasks.generateFor(今天)` → 任务号 `TK-<今天>-001`，唯一键 `planId@今日00:00`，重复点击"新生成 0 条"。
  3. `tasks.attemptCheckIn(taskId, P_CRACK, {labelRead:'NFC-B03-F2-CRACK01', method:'nfc'})` → 该点 `arrived`（**已到点待检查**）。
  4. 其余三点保持 `pending`（**待到点**）。
- **定位**：`/inspection` → 展开今日任务 `TK-<今天>-001`，高亮 `B03-F2-CRACK01`（已到点待检查）。
- **诚实标注**：NFC 为**模拟读卡**（界面已有 `NFC_DISCLAIMER`），不得写成"已接入读卡硬件"。

### M6 问题与工单 —— 场景键 `issuePool`

- **生成**：三条问题分别停在三种状态（身份 `safety` 做审核，`repair` 做接单）：
  | 目标状态 | 出处 | 关键数据 |
  | --- | --- | --- |
  | 待审核 `pending_review` | `issues.reportManualIssue()`（无角色门槛） | 楼栋 B01、测点 B01-F1-CHECK01、异常类型"外观破损"、描述含现场情况 |
  | 处理中 `repairing` | 事件转问题 → `reviewIssue(issueId,{action:'to_repair',category:'equipment',note:'…≥4字'})` → 工单 `assigned` → `repairing` | 来源=传感器预警，关联事件 `E*-001` |
  | 待复查 `pending_recheck` | 另一条问题 → `to_repair` → `assigned` → `repairing` → `submitted` → `verified` | 验收通过后问题**不关闭**，自动进待复查 |
- **注意**：`reviewIssue` 硬门槛 —— 审核意见 ≥4 字；`need_evidence`/`to_investigate`/`close_no_fault` ≥10 字；
  `close_no_fault+handled` 必须带照片或 ≥10 字免照片理由；已关闭问题一律拒绝。
- **定位**：`/issues` → 展开"待审核"那条，高亮状态标签。

### M7 工单闭环 —— 场景键 `workOrders`

- **生成**：四条工单覆盖四个状态（每条都从问题 `to_repair` 来，**转维修前先判 `ordersOfIssue(issueId)` 为空**）：
  | 工单状态 | 走到哪一步 | 关键数据 |
  | --- | --- | --- |
  | 待派工 `created` | 审核转维修即停 | 派工人未定；`dueAt` = 今天 +3 天 |
  | 处理中 `repairing` | `assigned`（safety，必填 `assignee='维修人员'`）→ `repairing`（repair，接单人=被派工人） | 维修措施未提交 |
  | 待验收 `submitted` | ↑ → 先 `attachments.add({kind:'after', workOrderId})` 拿照片 ID → `submitted{measures, materials, photos}` | 措施/材料/完工照片 2 张 |
  | 已验收 `verified` | ↑ → `advanceOrder(orderId,'verified',{note, acceptancePhotos:[draft]})` | 验收照片 `kind='acceptance'`、`workOrderId` 归属，与状态/日志**同事务**；问题同事务进待复查 |
- **物业代接**需写原因（≥ 非空）；接单人必须等于被派工人（`assignee` 存角色中文名，故按 `'维修人员'` 派工、以 `repair` 身份接单即可命中）。
- **定位**：`/issues` 的工单面板 → 展开 `WO-<今天>-002`（处理中），高亮完工照片缩略图。

### M8 复查观察期 —— 场景键 `recheck`

- **生成**：三条问题各覆盖一种复查形态（身份 `safety`）：
  | 形态 | 数据 |
  | --- | --- |
  | 复查逾期 | `registerRecheck(issueId,{subject:'复测裂缝宽度并留观', owner:'李老师（后勤保障处）', dueDate: 昨天})` → `overdueDays=1` |
  | 继续观察 | 上一条不填结论；另一条 `recordRecheckOutcome(issueId,{outcome:'observing', note:'…≥4字', nextDueDate: 今天+3天})` → 自动**开下一轮**（轮次 2） |
  | 复发转处置 | `recordRecheckOutcome(issueId,{outcome:'recurred', note:'复发，转处置'})` → 问题回 `pending_review` |
- **口径**：系统不下结论、逾期不自动关问题；`继续观察` 必须给下一次目标日期（否则被拒）。
- **定位**：`/issues` → 展开"复查逾期"那条，高亮"逾期 1 天"。

### M9 设备保养 —— 场景键 `maintenance`

- **生成**（身份 safety/property）：
  1. `maintenancePlans.savePlan({id:null, ...})` → 计划号 `MP-<今天>-001`：设备 `B03-F2-CRACK01-DEV1`（裂缝位移探头）、
     周期每周、负责人"李老师（后勤保障处）"、检查项 3 条（外观/基面/读数比对）、启用。
  2. `maintenanceTasks.generateForDay(今天)` → `MT-<今天>-001`（**今日待执行**）。
  3. `generateForDay(昨天)` + `execute(..., {answers 全答, measures, nextDueDate})` → **已完成历史**（`status='done'`）。
  4. `generateForDay(前天)` 不执行 → **逾期任务**（`status!=='done' && dueAt<now`）。
  5. 其中一条执行时勾一个异常项并 `createIssue` → 同事务产出问题：`source='maintenance'`（"保养发现"）、
     `submissionKey='mt_<taskId>'`、`maintenanceTaskId=taskId`，与任务**双向关联**；**事件数不变**。
- **硬规矩**：执行人须等于 `task.snapshot.owner`；有异常必须写描述；一周期只执行一次。
- **定位**：`/maintenance` → 保养台账定位到"裂缝位移探头"，高亮"下次保养日期（现场登记）"。
- **预期**：计划 1、任务 3（今日待执行 / 完成 1 / 逾期 1）、保养逾期 1 条任务，而**结构预警仍为 1 条事件**。

### M10 管理报表 —— 场景键 `reports`

- **生成**：不新增数据，校验并演示四类视图；确保三项指标**至少一项有分母、至少一项分母为 0**：
  - 有数据：把范围切到覆盖 M2/M9 的区间（如近 30 天）→ 预警事件 1 / 问题 ≥3 / 工单 4 / 保养任务 3。
  - 暂无数据：把范围切到 `2025-01-01 ~ 2025-01-31` → 显示"暂无数据"，**不得显示 0% 或 100%**。
  - 可导出明细：四张表各自"导出 CSV"，行数 = 页面条数（已实测：1 / 8 / 4 / 0 与之对应）。
  - 单事件报告：事件行 →「处置报告」→ 四段（为何预警／谁收到并确认／谁处置并验收／为何关闭），未确认/未关闭处**如实标注**。
- **定位**：`/reports` → 定位到事件表该行，操作按钮指向「处置报告」。

### M11（可选，独立开关）振动黄色演示 —— 场景键 `alarmVib`

- 仅当需要演示"振动绝对判定"时使用：`records.addRecord()` 写 3 条 `0.052 / 0.058 / 0.061 m/s²`，
  间隔 ≤5 分钟 → 生成**第二条**黄色事件。默认不载入，避免与 M4 的"一条事件"冲突。

## 7. 已知口径与风险（必须照实写）

1. **文件选择框**：照片走"合成 `File` 送入 `<input type="file">`"，**未经过 OS 选择框**；界面上不得写成"已真实选择文件"。
2. **打印**：报告页 `window.print()` 的打印对话框需人工确认；自动化只能核页面文字。
3. **工单建单不幂等**：`buildForIssue` 用随机主键，转维修前必须判 `ordersOfIssue(issueId).length === 0`。
4. **确认前必须 `events.load()`**：否则 `openEventOf` 读内存会把已存在事件误判成新建。
5. **不新增库表**可避免 v7→v8 迁移；若改为新增表，B1/B2/B3 的版本口径与 `nativeUpgrade` 测试需同步重跑。
6. 本功能会新增源码与测试文件，**会改变 README 记录的测试数/构建数基线**；V1 冻结验收（B2/B3/E4/E5/F2/F3/F4）
   仍未走完，二者需在同一轮里一起收口。
7. **填数值前必须知道的两条规则细节**（已核对 `src/core/assess/engine.ts`）：
   - 状态直接由**单条**判定的量级得出（`state = levelOf(trigger.value, thresholds)`），持续异常只把等级**往上抬**、
     不会下压。所以任一单条越过黄色阈值就会立即生成黄色事件 —— 这就是 M3 振动必须全部压在 0.05 以下的原因。
   - 速率规则用**带符号**速率（`(current - previous) / hours`，只有恶化方向 ≥ 阈值才升级）。
     故 M2 的 5 分钟复测段（0.54 → 0.53 → 0.53）虽瞬时变化率 0.12 mm/h，但方向是收敛，**不会被速率判成橙色**；
     反之若新增"快速恶化"数据，5 分钟间隔只要上升 0.01 mm 就会触橙。倾角与振动**没有**配速率规则。

## 8. 实施偏差（实现时改了什么，为什么）

1. **振动序列从趋势场景移到"振动预警事件"场景**，并在其开头加一条**低于阈值**的基线记录。
   原因：持续异常判定只看"按采样时间排序的最后几条"，而示例校区种子自带一条固定日期的越限振动记录
   （09-18 的 0.061 m/s²）。若本段写在它之前、或与它之间隔了几天，判定会因"相邻间隔 >5 分钟"返回 miss，
   等级升不到橙色。加一条低值记录把连续段断开，并把整段锚在"最近两天"，两个问题一起解决。
2. **取消"归档与恢复留痕"场景**。归档受"上级未归档才可恢复"等依赖约束，做成净零演示的失败面大于收益；
   在拿到明确的归档演示口径前不实现，避免出现"点一次把示例楼栋归档了却没恢复回来"的现场。
3. **预警场景确认的是站内提醒，不是事件本身**。一次写完 8 条记录后事件已进入"恢复待确认"，
   而事件级确认只接受"待确认"状态 —— 这是应用既有的状态机口径，场景不去绕开它，
   界面文案如实说明"事件级确认需在事件仍为待确认时操作"。
4. **保养计划周期用"每日"**（原设计写的是每周）。每周周期每天只命中一天，生成不出
   "今日待执行 / 已完成 / 逾期"三条并列的任务；每日周期才能同时展示台账、日历与逾期三种视图。
5. **新增「温湿度环境提醒」场景**（原设计里没有）。用途是给预警提醒补充**另一类**通知，
   并当面演示"环境异常不生成结构红色预警"这条边界；它同样锚在最近一天，理由与振动相同。
6. **预警场景把站内提醒处理成两种状态**（原设计只说"确认"）：先按演示策略把未确认提醒标记为超时升级，
   再由人确认其中 4 条 —— 预警提醒里于是同时有"已确认"和"已升级未确认"可看，而不是清一色已确认。
   超时升级调的是既有演示入口（`escalationSource = 'demo'`），真实系统按黄 30 / 橙 10 / 红 5 分钟判定。

## 9. 按审核意见收口（第二轮）

审核意见：**不做全局操作锁**（单人操作时临时切换演示身份没有并发写入风险），另列六项。处理如下：

1. **不做全局操作锁**：原来那个"已有场景正在载入，请稍候"的单值锁换成 `running: string[]`，
   只用于按钮自身显示"正在载入…"，其他场景的按钮不受影响。
2. **CSV 下载竞态已修**：`downloadCsv()` 的 `URL.revokeObjectURL` 推到下一个宏任务；真机复验下载事件不再被取消。
3. **三态状态**：`已就绪 / 失败 / 数据已失效`。失败会写一条 `状态=失败` 的登记日志（界面显示"上次载入失败 · 可重试"）；
   **数据已失效**的判定不能靠日志 —— 清库/重载示例校区/导入备份都会整表重建数据集与日志表，
   于是界面状态改存 localStorage（`stores/demo/registry.ts`），并由 `archive.ts` 在这三处打重置时刻标记。
   **审计留痕仍照常写操作日志**（`objectId='demo:<场景键>'`、`reason` 以 `状态=成功/失败` 开头），两件事分开。
4. **全链遇前置失败即停**：新增 `FULL_CHAIN_DEPS`（建档是所有写数据场景的地基；裂缝预警还要先有监测主链），
   前置未成功时后续步骤标"跳过：前置 X 未成功"，不再拿着半截数据继续写。
5. **冲突不静默**：记录序列在跳过时区分"自己上次写的"与"已有非演示记录"，后者计入冲突条数并写进结果说明；
   问题池与复查在拿到不属于本场景的问题时提示"与既有问题冲突，跳过、未审核"。
6. **载入后定位**：三个预警场景给出 `/alarms?event=<id>`；问题池/工单/复查沿用 `?issue=`（该页有行高亮 `row--flash`）；
   保养沿用 `?task=`。**事件页靠打开详情定位，没有行高亮样式** —— 这点照实说明，没有假装有。

## 10. 红色预警现场处置（单人答辩顺序）

「系统设置 → 演示场景 → 一键准备红色预警现场处置」与「一键载入全链」是两个独立入口。前者只通过正常录入路径补入 4 条裂缝历史记录，按规则形成黄、橙、红 3 条证据、2 次升级和 7 条站内通知，把事件停在**红色、待确认**；不预建问题或工单。页面跳转到事件详情，同时显示红色强提醒。再次点击只重新展示提醒，不重复建记录或事件。若同一采样时刻已有非本场景记录，或事件已被处置，入口拒绝并说明冲突，不覆盖原数据。

现场按以下顺序演示，每一步都由对应身份实际操作，不通过脚本直接改状态：

1. 安全管理人员点击红色提醒的「查看并处置」，核对测点、基准、黄橙红证据与通知，再点「确认事件」。
2. 在事件详情点「转问题处理」，登记现场核查结果。演示维修分支时，写明**测点支架固定件松动**；疑似承重结构异常应选「转专业排查」，不得演示为物业直接修补结构。
3. 安全管理人员在问题池审核「转维修工单」，检查问题与工单编号互相可追溯，然后指定维修人、期限和现场要求。
4. 切换维修人员身份接单，填写措施、材料并附维修后照片，提交待验收。安全管理人员核查照片及措施，可退回返工或验收通过。
5. 工单验收通过后，问题进入待复查；登记复查事项、责任人和目标日期，再现场选择「确认恢复」「继续观察」或「复发转处置」。
6. 事件不会因工单验收或问题复查自动关闭。需继续录入满足规则的连续恢复复测，且具备本事件关联工单验收依据或安全管理人员的现场「无需维修」核查结论，才能授权关闭。最后查看事件、问题、工单时间线及操作日志。

答辩口径：4 条读数均是**历史补录**，弹窗表示「刚在本机录入并判定的演示预警」，不表示传感器正在实时上传；通知是本机站内提醒，不声称短信、电话或云端送达。演示阈值用于验证流程，不作为建筑安全鉴定标准。原始 Word 计划不随本工程改动。
