# 查寝与筑瞳同时运行

2026-10-18 核验：原配置都使用宿主机后端 8000、开发前端 5173，会在同时启动时冲突。
保留查寝配置，仅调整筑瞳的配置和启动说明。

| 项目 | 页面入口 | 后端 |
| --- | --- | --- |
| 查寝 | http://127.0.0.1:5173 | http://127.0.0.1:8000 |
| 筑瞳 Docker | http://127.0.0.1:8080 | http://127.0.0.1:18000 |
| 筑瞳本地开发 | http://127.0.0.1:5180 | 同上 |
| 筑瞳本地预览 | http://127.0.0.1:4173 | 同上 |

## 筑瞳启动

推荐在项目根目录执行 `docker compose -f deploy/compose.yaml up --build -d`，访问 8080。
无需另外启动本地 uvicorn。需要开发时另开终端执行 `npm run dev`，5180 的 `/api` 代理到 18000。
本地 `npm run serve` 也使用相同代理，保留已有 4173 来源下的浏览器数据。

不使用 Docker 时，按 [后端启动说明](../../backend/README.md) 启动本地后端 18000。
本地后端与 Docker 后端二选一；两者不能同时绑定筑瞳的 18000。
开发和预览启用 strictPort，端口被占用会明确报错，不自动漂移到其他项目的端口。

Docker API 容器内部继续使用 8000，宿主机映射为 `127.0.0.1:18000:8000`。
Nginx 通过筑瞳的独立 Compose 网络请求 `api:8000`，不请求宿主机的查寝服务。
数据库继续使用原 `zhutong_runtime` 数据卷；此次没有删除或更换数据卷。

## 查寝启动

使用查寝项目原有的「一键打开查寝系统.bat」，默认后端 8000、前端 5173。
此次验证已启动查寝后端和前端；仍运行时无需重复启动前端，否则原启动器可能选择下一个空闲端口。
未修改查寝源代码或端口配置。

## 实际核验

- 两个数据库就绪接口同时返回 HTTP 200，查寝为 `database: ok`，筑瞳为 `database: sqlite`。
- 查寝 5173 的代理返回查寝 API 标题；筑瞳 8080 返回五类演示身份，确认各自连接正确。
- 筑瞳 5180 开发代理、4173 预览代理均返回筑瞳就绪状态。
- 两个页面入口返回各自页面标题；Docker API healthy，迁移任务退出码 0。
- 筑瞳后端 66 项测试、Ruff、前端类型检查及 Docker 构建通过。

具体时间和访问结果见 [核验数据](evidence/port-coexistence-check.json)。
本次验证页面与 API 连通性，没有执行查寝业务写入操作。
早期阶段文档中的 8000、5173 为历史核验地址，当前以本文及启动说明为准。
