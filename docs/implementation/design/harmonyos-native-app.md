# 筑瞳 App：OpenHarmony原生技术与范围决策

计划修订：2026-10-24。依据通知赛题3与用户最新要求：App使用完整OpenHarmony原生框架，API≥12。
本文替代先前 Flutter/Dart、Android/APK 路线；历史完成报告保留原样，不代表 App 已经实现。
规则、模拟硬件边界和提交格式以[赛题对照](competition-scope.md)为准。

## 技术决策

| 层次 | 新方案 | 验证点 |
| --- | --- | --- |
| 应用语言 | ArkTS | 在锁定 SDK 的严格检查下通过，不直接复制 Vue/TypeScript 实现 |
| 界面 | ArkUI 声明式原生组件 | 任务、上报、工单、设置均原生绘制；不采用 WebView 包装业务页 |
| 应用模型 | Stage、UIAbility | 前后台、页面返回、权限和窗口变化正确处理 |
| 工具链 | DevEco Studio、兼容OpenHarmony的SDK、Hvigor、OHPM | API≥12，固定实际安装版本、锁文件、可复现构建任务 |
| 网络 | OpenHarmony原生HTTP/连接能力 | 访问现有 FastAPI，保留身份、范围、幂等、rev、epoch 契约 |
| 本地数据 | OpenHarmony关系型数据库relationalStore；应用私有文件目录 | 快照、草稿、队列落本地关系库；照片字节入文件目录 |
| 照片 | 目标OpenHarmony版本可用的系统拍照、照片选择和图片处理 | 真机采集/选择、压缩、权限拒绝、上传、原件核验 |
| 到点 | 人工签到；明确标注的模拟读卡 | 本轮不开发真实NFC；若未来扩展需单独验证设备与标签 |
| 测试 | 锁定 SDK 支持的 ArkTS 单测、UI 自动化、设备调试工具 | DevEco/Hvigor 构建检查与真机回归，记录真实任务名和退出码 |
| 安装与参赛包 | 签名 HAP；按赛事分发要求提供 APP 发布包等必要材料 | HAP 安装验收；调试签名、发布签名和证书有效期分开记录 |

App 不引入 Flutter、React Native、uni-app、Android 兼容容器或跨端 UI 运行时。
优先使用系统能力和原生组件；确需依赖时仅引入经审查的鸿蒙原生库，记录版本、许可和离线可用性。
Web 继续 Vue3/Vite，服务端继续 FastAPI+SQLite+Alembic+uv+Docker；两端共享服务端数据与业务契约。
“完全鸿蒙”限定为本次 App 的框架、页面和设备能力，不把现有服务器改造成手机内嵌服务。

## 版本与参赛条件冻结

已确认：第三届河南省高等学校信息技术应用创新大赛，赛题3，DevEco Studio、OpenHarmony、API12及以上。
用户决定不开发南向硬件，全部监测输入模拟。
2026-10-26已实测OpenHarmony公共SDK6.0.0.47/API20（Beta1组件）+DevEco6.1.1.418/Hvigor6.24.5，
在Pura 90模拟器（HarmonyOS镜像标签、OpenHarmony核心API24）完成调试签名包与平台能力核验。
见[记录](../handoff/reports/mobile/03-native-platform-probe.md)；真机/赛事运行环境、正式签名与业务能力仍未验收。
按OpenHarmony原生应用规划，不将商业HarmonyOS的SDK专有Kit或设备兼容性自动当作OpenHarmony支持。
阶段8首个门槛必须核对：

1. 复核赛题对照表中的指定平台、匿名DOCX/PPT/≤5分钟且≤100MB的MP4、RAR要求和后续通知。
2. DevEco Studio、SDK/API、ArkTS、Hvigor、OHPM 实际版本及相互兼容关系；是否需要离线依赖缓存。
3. 目标OpenHarmony设备/兼容运行环境型号、系统/API、签名安装权限、调试连接、NFC与相机能力。
4. compatibleSdkVersion/targetSdkVersion、bundleName、签名配置和安装命令，随工程形成版本清单。
5. 原生网络请求、图片选择、沙箱文件、关系库各做一个最小真机实验，成功后再铺业务。

先做SDK/API≥12编译和安装验证；设备厂商/赛事提供的运行环境是否兼容须留证，不能仅凭“鸿蒙手机”名称判定。
精确 API 和命令以锁定OpenHarmony版本的官方文档及实测为准；不虚构已安装 DevEco 或已具备真机。
HAP 调试安装成功不等于满足发布/参赛分发条件；无设备时只能记录模拟器或预览器结果。

## App 信息架构

底部四入口：**工作台、监测、任务、我的**；任务内分点检/巡检/工单，上报为明确的主要行动入口。

| 页面组 | 必须保留的内容 | 亲和设计落点 |
| --- | --- | --- |
| 工作台 | 我的待办、处理中、待同步、当前身份与数据更新时间 | 校园插画、小瞳问候、明确下一步；统计全部来自服务端/已标明的本地快照 |
| 监测/设备 | 三类测点当前值、单位、采样时间、在线/电量、建筑/楼层/类型筛选 | 楼栋图案与读数卡，源为模拟时持续可见；缺值不显示正常 |
| 预警/维护台账 | 当前与历史事件、授权确认、现场排查/处置措施、历史记录 | 状态时间线和行动按钮，关闭按服务端条件执行 |
| 统计 | 预警频次、传感器类型分布、周/月趋势 | 轻量原生图表与可读文本，从数据库聚合，不放假曲线 |
| 任务列表/详情 | 类型、时间、位置、计划快照、必查点、检查进度 | 图文任务卡、楼栋小图案、简明进度；不能用动画代替真实完成 |
| 到点与检查 | 模拟读卡、人工原因、检查清单、正常/异常、备注 | 分步向导、可达大按钮、当前点位与状态图标 |
| 问题上报 | 来源、关联任务/测点、异常描述、照片、提交回执 | 清楚的照片槽位、现场记录卡、可恢复草稿和上传反馈 |
| 工单办理 | 接单、措施、前后照片、完工、退回理由、时间线 | 处理步骤轨迹、维修工具插画；“完工”与“验收”明确区分 |
| 我的/设置 | 身份切换、连接、同步中心、权限帮助、版本 | 小瞳说明卡；不出现登录、注册、密码页 |

首版必须覆盖赛题北向监测、预警确认/排查/处置和统计，再突出点检、巡检、问题上报与工单现场办理。
审核、派工、工单验收和管理仍以Web为主；App的预警确认与措施登记不能仅用Web入口代替。
小瞳可后置提供当前任务的只读帮助/知识入口，复用阶段7服务，不复制整套 Web 视觉与导演能力。

## 结构与端间边界

拟在仓库建立 `mobile/openharmony/`，由 DevEco 创建标准工程，不伪造可构建模板。
应用内按 `features/{workbench,monitoring,alarms,tasks,report,orders,profile}`、`core/{network,identity,storage,sync}`、
`shared/{components,models,theme}` 分层；资源与设备能力适配分开。保留单 entry 模块起步，不为展示拆大量 HAP。
每个页面只编排状态和交互；DTO、业务操作、文件生命周期和网络客户端不堆入页面 build 函数。
ArkTS/.ets 文件尽量≤450行、函数≤80行、参数≤5，目录文件尽量≤8。

- 共享的是 OpenAPI/JSON 契约、错误码、业务规则、视觉 token 和素材规范；不直接共享 Vue/Pinia 运行时代码。
- 远程实体、当前草稿、已入队快照分开；服务端仍是权威，本地关系库不能直连/复制服务端 SQLite 文件。
- 后端 Alembic 管理服务端迁移；App 本地 schema 由原生关系库升级流程管理并单独测试。
- LAN 真机通过电脑局域网地址访问8080同源API；手机127.0.0.1不是电脑。连接设置独立展示。
- 首次连接记录实际协议、系统网络配置与权限；若局域网演示使用HTTP，按锁定SDK配置受控演示入口，
  不通过全局关闭证书校验解决连接问题。正常HTTPS链路保持证书校验。
- 生命周期变化可能中止任务；阶段9采用持久队列、回前台和手动同步，不承诺无限后台驻留。
- 不接外部AI API，不把图片压缩、扫码或NFC读取包装成建筑安全鉴定或真实到场证明。

## 鸿蒙特色的优先级

| 等级 | 内容 | 完成条件 |
| --- | --- | --- |
| 必做 | ArkUI原生交互、系统图片/拍照流程、原生关系库草稿队列、生命周期恢复、窗口适配 | 阶段8/9设备及数据对账通过 |
| 必做 | 手机单栏、宽窗口/平板列表详情适配 | 先有原型和预览证据；只有真机实测才声明对应设备已支持 |
| 后置，不在本轮 | 真实NFC标签读取→测点匹配→检查页 | 后续另定范围；实际接口/标签/权限/错标签和生命周期均需实测 |
| 可选展示增强 | 原生服务卡片“今日待办/待同步” | 业务核心通过后，卡片刷新、身份范围、点击导航与来源时间明确 |
| 后置扩展 | 真正跨设备流转、分布式协作、穿戴端 | 不纳入当前必交承诺；需赛规/设备/时间明确后另立任务 |

Web与App共享API形成业务协同，不宣传为鸿蒙分布式软总线或系统级跨设备流转。
真实NFC未验收时以人工签到和显式模拟路径展示，不影响原生技术路线，但不计入真实NFC成果。

2026-10-26落地更新：mobile/openharmony已建立原生在线业务工程，四入口/监测详情/五身份接真实后端。
App界面按用户本轮要求采用[校园守护手账设计](app-cartoon-ui.md)，含原创小瞳、卡片、插画、触屏弹性和动效偏好。
编译安装与手机模拟器证据见[本轮报告](../handoff/reports/mobile/04-native-online-ui.md)；现场写入和真机仍按阶段8验收。
