## 全阶段约束

1. 比赛演示使用真实后端和持久化，保留原界面与业务语义，不扩为企业级平台。
2. 无登录页、账号密码；五类预置身份由后端核验，身份提示不能当权限凭据。
3. 已迁移模块日常读写走服务端；Pinia 是视图状态，不能成为另一份权威数据库。
4. 后端不可用时保留草稿并提示，不静默回退本地业务写入；阶段 9 离线队列必须明确显示待同步。
5. 新写操作记录审计、幂等回执、版本信息；业务结果、关联、审计和回执在同一事务。
6. expectedRev 是乐观锁行版本；监测历史修订次数单独使用 recordRevision，不混用旧 revision=0。
7. datasetEpoch 用于隔离复位前请求；从阶段 4 定义，阶段 9、10 完整验证。
8. 文件字节保存在持久化文件目录；SQLite 存元数据与哈希。避免将 base64、临时 URL 当持久化内容。
9. 所有新迁移为追加版本，不改写 0001—0008。现版本目录已有 8 个文件，新增前规划版本子目录并验证 Alembic 能发现全部版本。
10. Python/JS/TS/Vue 文件尽量 ≤450 行，Dart ≤500 行；函数 ≤80 行，参数 ≤5 个，目录文件尽量 ≤8。
11. 只拆接入必需结构；发现已有结构债要记录风险及最小方案，大范围重构先单独确认。
12. AI 仅在阶段 6—7 接入已确认的本地方案；无外部模型 API、无依据不编造；模拟数据和演示规则明确标记。
13. 采样时间、录入时间、真实时钟与演示时钟分开；接口明确时区，业务日期按 Asia/Shanghai，旧时间原值保留可查。

7. 使用 [完成度报告模板](completion-report.md) 提交审核；审核通过后再更新已通过状态及阶段标签。

## 证据与审核规则

每个验收编号记录四态：未实现、已实现未验证、验证通过、验证失败。
完成比例按“验证通过项/该阶段必验项”计算；子项不齐不能整项通过。
允许报告进展百分比，但它不是验收结论。缺少代码或运行证据时，结论只能是未验证。

审核依次检查：需求与范围→实现与结构→自动测试→真实运行→数据一致性与回归。
有代码访问条件时会读 diff 并复跑必要检查；只有报告时只做材料审核，明确证据限制。
截图不能单独证明持久化、权限、幂等或事务正确，必须配接口/数据库/测试证据。
审核默认只读，不自动代写实现或修复；发现问题给出定位、复现、风险及最小修复建议。

| 审核结论 | 使用条件 |
| --- | --- |
| 通过 | 必验项全部有可信证据，当前阶段无阻断缺陷 |
| 不通过 | 有可复现的功能、数据、权限或阶段范围缺口 |
| 待补证据 | 描述可能已完成，但代码、测试或真实运行不足以确认 |

问题按 P0（数据丢失/串库/敏感凭据泄漏等）、P1（主链路失败/越权/重复写入等）、
P2（局部功能或恢复体验问题）、P3（非阻断展示/文档问题）分级。
与必验项直接相关的缺陷即使不是 P0/P1，也须修复后才能通过对应项。
可延期项必须写明原因、影响、去向，不以口头“演示够用”替代已约定的闭环。
