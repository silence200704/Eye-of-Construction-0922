# 阶段 5 实施提示词

将下文整体发送给实施开发的任务：

```text
在现有筑瞳项目上实施阶段 5：点检巡检、问题、工单、复查、保养与报表的后端迁移和 Web 接入。
阶段 4 已通过；请直接开始实施，逐个子步骤完成并核验，不只给计划。完成阶段 5 后提交审核，
不要自行进入阶段 6，也不要在审核前将实施台账标成通过。

先阅读：
- 用户提供的 AGENTS.md 和仓库实际适用的规则；
- docs/implementation/README.md、handoff/README.md；
- docs/implementation/stages/04-monitoring.md；
- docs/implementation/contracts/monitoring-v1.md；
- docs/implementation/handoff/stages/05-field-work.md、handoff/completion-report.md；
- 现有 inspection、maintenance、issue、work-order、recheck、report、media 的实现与测试。
先记录已有业务行为、状态转移和权限矩阵，再冻结阶段 5 接口契约。以详细计划 S5-01—S5-12 为验收依据。

范围约束：
保留 Vue 3/TypeScript/Vite 及现有界面，使用 FastAPI/SQLAlchemy/SQLite/Alembic/uv/Docker。
比赛演示使用真实数据库和文件存储，不扩成企业平台。本阶段不改 AI，不接外部模型 API，
不开发 Flutter 和阶段 10 演示控制。无登录页、账号密码，仅五类预置身份切换。
筑瞳使用 8080/18000、本地开发 5180；查寝保留 5173/8000，不停止或改动查寝服务。
不得重置 demo-main、清空 Docker 卷、伪造截图或覆盖已有迁移和历史证据。

统一基础：
复用阶段 4 的 Workspace/Command、服务端身份与楼栋范围、expectedRev、X-Dataset-Epoch、
Idempotency-Key、目标参与摘要、审计与回执。业务修改、双向关联、附件归属、审计与回执同事务。
写会话保留 Depends(write_session, scope="function")，提交成功后才返回成功；中途与最外层提交失败均回滚。
检查既有表与媒体接口并优先复用，确有需要时追加 Alembic，不改写已发布迁移。
正式字段承载业务；legacy_payload 仅溯源，不把新业务全塞进万能 JSON。

按以下顺序做可运行的完整业务动作，每一小步完成后运行相关测试并记录核验结果：

1. 计划、任务、逐点检查
保留点检/巡检、设备/路线、周期、范围、清单、执行角色和启停。重复生成不重复任务，
任务冻结生成时快照；改计划不改变已有任务。虚拟 NFC 校验标签和版本，人工签到必须写原因，
成功失败尝试均留痕。到点不等于完成，未答必答项、漏检、异常没有后续处置依据不得完成。

2. 上报与问题审核
支持传感器、巡检、人工、保养四种来源并保留原始描述、位置、来源链和照片。
一次上报固定 submissionId，重试复用；独立上报不能按同人同日或时间桶误合并。
保留六种审核出口：转维修、转专业排查、安排复查、退回补充、关联已有对象、无需处理关闭。
保留二级分类、审核说明、无照片原因和原报告；关联目标必须真实存在、范围正确、不能自关联，
双向关系同事务，已关闭目标按原规则要求说明。疑似重复由人工判断，不自动删除合并。

3. 工单、验收、复查与事件关闭
落地 created→assigned→repairing→submitted→verified/returned 及退回再办理。
派工指定维修人；维修人只能接自己的单，物业代接沿用原规则并留原因；safety 验收，维修人不能自行验收。
完工措施、证据与验收退回理由依原规则校验。工单验收只推进问题 pending_recheck，不能直接关闭问题或预警。
复查保留责任人、日期、每轮证据及历史：recovered 关闭、observing 安排下一轮、recurred 回待审核继续处置。
接通事件关闭的“当前事件关联已验收工单”与“合法无需维修依据”两种分支，
两种分支都必须复用阶段 4 current_recovery 对实际有效采样序列核验；不能只信 recovering 字段，
不能借同测点旧事件工单关闭。保留恢复窗口任意记录修订、旧证据修订、过期状态的全部回归。
任务完成、工单验收、问题关闭、预警关闭是四个独立结果，不共用一个 done。

4. 附件与保养
真实文件存私有持久化目录，SQLite 存元数据及哈希；复用上传、内容读取及授权。
每归属最多三张、合计 600 KB，服务端检查数量、体积、类型、所有权与唯一业务归属。
draftId/mediaId 支持上传后补关联和重试，不重复建文件或占配额，未上传成功不得显示为证据已提交。
保养计划、周期任务、清单、执行结果、下次日期及历史落库；异常转问题双向关联同事务，重试只建一次。

5. Web 与报表收口
任务、问题池、工单、复查、保养、报表、单事件打印与 CSV 全部使用服务端真实读取。
明确指标粒度、时间范围、归档口径，观察中不算最终闭环，验收率不冒充问题关闭率。
逐一列出并迁移日常业务 IndexedDB 写入口；API 不可用时明确失败并保留草稿，不伪装本地成功。
共享命令结果、冲突刷新和错误显示。旧助手与自动演示写入口在对应后续阶段接通前保持暂停，
不能绕过后端形成混合数据。无需本阶段另造“历史发现补建问题”专项功能。

验证与结构：
关键业务先实际运行失败测试，再实现并保留 RED/GREEN 证据。覆盖成功、角色/范围越权、字段错误、
rev/epoch 冲突、同键重放/异载荷冲突、并发重复生成、中途故障与最外层提交故障回滚。
动态语言文件尽量 ≤450 行，函数 ≤80 行，参数 ≤5 个，直接文件尽量 ≤8；超限先做最小 DTO/Context 或拆分。
递归结构门禁不能跳过新子目录，已有满额目录应分组，不继续堆文件；不做未授权大范围重构。
后端完整 pytest 覆盖率至少 80%、Ruff、format --check，前端 test、test:tooling、typecheck、build 均通过。

真实运行至少展示：
- 设备问题→维修→验收→复查恢复；
- 结构问题→专业排查/观察→复发；
- 保养异常转问题、退回补充、验收退回各一次。
核对每次状态变化的对象 ID、关联、附件实际字节、审计和回执；刷新、重启和另一浏览器仍一致。
重建筑瞳容器，验证备份→校验→独立目录恢复，前后对照原数据，复验查寝和筑瞳端口同时可用。
自动测试通过不替代真实 HTTP 和页面业务验证；证据仅用独立测试库或明确标识的测试数据。

交付：
提交阶段 5 契约、状态/权限矩阵、逐项 S5-01—S5-12 完成度报告、实际命令与退出码、提交 SHA、
真实运行证据及备份清单。每项使用未实现/已实现未验证/验证通过/验证失败，缺证据不能写通过。
报告明确残留 IndexedDB、暂停入口、已知限制及未完成项。阶段 5 状态设为“待审核”，等待审核结论。
```
