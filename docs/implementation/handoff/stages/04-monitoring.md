# 阶段 4：档案、监测与预警

目标：档案和监测主链路真实写入 SQLite，地图、看板、趋势、事件与通知读取同一服务端事实。
前置：阶段 3 已通过；对当前数据库和媒体做升级前备份。
本阶段不改助手回答逻辑，不扩展真实传感器、短信、推送和企业权限管理。

## 实施步骤

### 4.1 冻结行为与共用写入约定

- 阅读 archive/records/events stores、core/assess、core/event、core/rules、core/csv 和现有测试。
- 建立 TS 旧引擎与 Python 新引擎共用的输入/预期样例：缺项、阈值边界、速率、持续异常、恢复、历史补录、修订。
- 确认每个动作允许的五类身份及楼栋范围；写请求不接受客户端 actor/scope 充当授权。
- 统一写入上下文：datasetId、datasetEpoch、expectedRev、Idempotency-Key、服务端身份与时间。
- 幂等范围至少含数据集、epoch、身份、操作、键；同键同内容复用，同键不同内容返回冲突。
- 幂等回执和业务修改同事务；版本冲突不覆盖；复位前 epoch 不允许继续写。
- HTTP 客户端目前只返回 data；增加保留 rev/replayed/requestId 的命令结果通道，兼容已有读取调用。
- 监测旧修订次数 recordRevision 与服务端 rev 分开；不得用前端旧 revision=0 做乐观锁。

### 4.2 档案读写

- 先实现楼栋、楼层、测点、设备查询及必要分页/范围筛选，再实现建档、修改、归档。
- 保留编号、来源、负责人、位置历史、标签、图纸版本和审计，不硬删除有历史引用的对象。
- 校验楼层属于楼栋、测点位置 0—1、设备绑定与量程、启用 NFC 标签唯一性。
- 已归档对象仍能解释历史；禁止不合规新录入，保留查阅入口。
- 基准修改生成新版本，记录生效时间与原因；历史按采样时刻取相应版本。

### 4.3 规则与监测引擎

- 实现规则稳定标识、版本、启停、生效时间、适用楼栋/测点及阈值查询和变更。
- 修改规则新增版本，保留历史；不把“读取时用最新规则重算”当历史解释。
- 将质量校验、单位/量程、数值、相对基准、速率、持续异常、恢复判定迁移为可独立测试的服务端逻辑。
- 监测录入、修订、试算使用相同引擎；试算只读，不产生业务事件或通知。
- 修订保留原值、原快照及修订原因，替代证据可追踪；补录不得错误覆盖当前最新状态。

### 4.4 监测事务与 CSV

- 一次正式录入/修订的记录、判定、事件变化、通知、审计、回执同事务。
- CSV 先逐行预览，保留行号、错误和有效行；确认只提交选择的有效行，错误行不写入。
- 明确批次语义：本计划采用选中有效行整批原子提交；任一提交时冲突则整批不落库并返回逐行原因。
- 预览和确认之间重读规则、对象状态与版本；有变化则返回冲突并要求重新预览，不沿用过期判定。
- 重试同一批次不重复写入；CSV 与手工录入对同一输入必须产生一致结果。

### 4.5 事件、通知及展示

- 迁移 pending→handling→recovering→closed 的合法动作与权限；不允许任意 PATCH 状态。
- 同数据集、测点、稳定规则只有一个未关闭事件；追加证据、历史最高等级和升级历史分别保存。
- 恢复不自动关闭；关闭要满足原恢复条件、学校安全管理身份及处置依据。
- 阶段 4 支持原有“无需维修现场核查依据”分支；阶段 5 再接通关联已验收工单分支，不能提前伪造工单依据。
- 通知区分生成、展示、确认、超时升级；只有实际展示才登记 presentedAt，不冒充短信送达。
- 超时核验由显式命令和服务端时间执行；模拟时钟隔离到阶段 10 演示机制。
- 切换看板、地图 2D/3D、趋势、记录和预警详情的数据适配；保留图形组件与交互风格。
- 读数与版本的历史展示一致；新动作成功后重新取服务端结果，失败不显示“已保存”。
- 全量排查助手准备、手动演示和自动演示的旧写入口：已迁移部分使用后端适配，未接通部分在后端模式明确暂停并说明阶段去向，不能继续向 IndexedDB 写另一份结果。

## 建议接口与交付物

在 `/api/v1/datasets/{id}` 下规划 buildings/floors/points/devices、baselines/versions、rules/versions、
records/revisions、records/import-preview、records/import、assessments/preview、
events 及 acknowledge/close 命令、notifications 的 present/acknowledge/escalate 命令。
这些是资源建议，实施时先提交正式契约，复用既有信封与身份依赖。

交付：接口契约、权限矩阵、版本/事务设计、共同判定样例、Web 接入、追加迁移、测试与真实操作证据。
读取新业务列与快照；legacy_payload 仅用于溯源，不能成为可写万能 JSON 接口。

## 必验清单

| 编号 | 验收条件 |
| --- | --- |
| S4-01 | 建档/修改/归档持久化；跨浏览器可读；无效楼层/坐标/重复标签被拒绝 |
| S4-02 | 基准与规则新增版本，历史样本仍引用原生效版本；旧 recordRevision=0 正确保留 |
| S4-03 | 旧新引擎共同样例全部一致；缺项、质量排除、单位、量程和阈值边界明确 |
| S4-04 | 手工录入与修订保留原值及替代证据；历史补录不错误改变当前状态 |
| S4-05 | CSV 逐行预检、有效行整批提交、过期预检及提交冲突回滚符合约定 |
| S4-06 | 同次重试只写一次；同键不同内容冲突；过期 rev/epoch 不覆盖、不建新事件 |
| S4-07 | 黄→橙→红升级仅一条未关闭事件；恢复不自动关闭；错误角色和缺依据无法关闭 |
| S4-08 | 通知生成/展示/确认/升级分别留痕，不重复升级，不冒充外部通知 |
| S4-09 | 看板、地图、趋势、详情读服务端；断开 API 后写入失败可见，无本地成功假象 |
| S4-10 | 注入中途失败后记录、事件、通知、审计、回执整体回滚，无半条业务 |
| S4-11 | 五类身份和楼栋范围服务端校验；伪造 actor、对象 ID 或跨数据集访问无效 |
| S4-12 | 旧库/空库升级、重启、备份恢复及前序测试通过；查寝与筑瞳可同时访问 |

真实操作至少提供一次建档、一次黄橙红升级、一次修订/补录、一次 CSV 冲突、一次合法关闭。
报告附对象 ID、版本、事件/通知/审计/回执数量变化及跨浏览器截图。
阶段 5 接通工单后须复验关闭依据，阶段 10 接通演示时钟后须复验通知超时。
