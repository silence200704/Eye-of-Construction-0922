# 问筑瞳：演示 AI 联动方案与进度

更新日期：2026-09-30。本文是后续对话的持续记录；每轮核验后更新「当前状态、未通过项、下一步提示词」。**用户已决定放弃旧 Word 计划，本文件是当前开发与验收依据**；旧 Word 保留作历史资料，不再驱动实施。目标是**纯前端演示 Demo**，真实服务端协作、真实传感器／摄像头／实体 NFC 不纳入交付，也不得写成已实现。

## 1. 要达到的演示效果

参观者说一句话，半屏小瞳能回答「发生了什么、依据是什么、去哪里看、接下来能演示什么」；演示者可以点一次按钮让系统定位到对应的看板、测点、影像或事件。需要补入测试数据时，先显示将产生的对象和数据来源，由演示者确认，再调用**现有演示场景入口**。执行后小瞳读取实际结果，给出事件号、问题号、工单号以及成功、跳过或失败的回执。不得把“准备了剧本”当成“业务流程已完成”。

核心价值是让外行人沿着同一条对象链看懂系统，而不是新增一个会自由生成答案的聊天模型：

`一句自然问法 → 确定性意图与对象消歧 → 同源只读快照 → 证据卡 → 可点的下一步 → 确认后的演示场景 → 重读实际结果`。

## 3. 产品界面：半屏“讲解／带我演示”双模式

半屏面板头部保留小瞳形象和当前对象标签（例如 `3号教学楼 · B03-F2-CRACK01 · E20260918-001`）。主体只显示一张正在讲解的证据卡和一张下一步卡，避免把所有按钮、表格、规则同时堆进半屏。底部保留输入框与 4 个快捷问法：`全校现在什么情况`、`这个测点怎么样`、`为什么是红色`、`带我演示处理流程`。没有明确对象时先让人选测点／事件，不默选同名对象。

- **讲解模式**：只读。结论下面给关键值、单位、采样时间、录入时间、来源、质量、规则版本、原始记录号；解释“演示补录／无设备心跳”。按钮只导航或高亮，不写库。
- **带我演示模式**：顶部显示 `步骤 2/6 · 预警已出现`、当前对象编号、下一步以及进度。每步仅一个主按钮和一个“跳过／返回”辅助按钮。跳转后保留同一事件上下文；回到小瞳可继续。
- **受控指令卡**：显示“将写入什么／不会写入什么／是否已有同键数据／失败如何重试”，再让演示者确认。提问本身和打开确认框都不写库。
- **执行回执卡**：从仓储返回值与重新读取的对象生成，不从剧本文字推断。分别显示“新增 N／跳过 N／失败原因”和可点的对象编号。场景部分失败时停在该步，不显示后续步骤已完成。
- **红色提醒优先**：红色弹窗出现时暂停小瞳装饰动效，提醒在最上层；演示者处理或稍后处理后可回到导览。不要让半屏面板自动盖住提醒。

## 4. 六个固定演示任务

| 用户说法或点击 | 小瞳做什么 | 写入边界与成功证据 |
| --- | --- | --- |
| “现在全校监测情况怎么样？” | 读取看板同源快照，报在册测点、最近有效采样、未关闭事件；按钮“看传感器驾驶舱” | 只读；数据为零时说“暂无数据” |
| “这个裂缝传感器怎么样／为什么红？” | 定位明确测点与事件，展示读数、相对基准变化、黄橙红证据、规则版本；打开趋势或事件详情 | 只读；不能自己重算等级或推断实时在线 |
| “准备红色预警演示” | 展示当前已有确认卡，确认后复用 `liveResponse` 场景，弹红色强提醒，再读真实事件编号 | 现有唯一已接通写入；重复执行按场景幂等，冲突不覆盖手工记录 |
| “带我看照片有什么变化” | 导航到当前测点影像页，提示点“一键加入前后照片”、框选同一区域；之后回答像素差与来源 | 演示图标“生成素材”；影像会话不写库，不自动建预警或给毫米数 |
| “演示巡检到点” | 定位到演示任务的指定点位，展示“错码失败 → 正确模拟 NFC → 提交到点”的步骤卡 | 先核对任务和身份；到点仍由现有任务仓储判定；明确“模拟读卡” |
| “这个预警下一步怎么办／带我看维修闭环” | 展示事件→问题→工单→验收→复查→授权关闭的当前节点与下一可达页面 | 可为展示预置既有全链场景，但必须先确认；实际派工／验收／关闭由原业务入口与权限判定；不自动代人写结论 |

演示路径可从任一对象中途进入；如果已经有事件或工单，小瞳从实际状态继续，不再创建第二条。对不存在、已关闭或归属不一致的对象，直接给原因与重新选择入口。

## 5. 实现方式：复用而不重造

1. **识别层**：在现有确定性 `parse.ts` 中加入有限的“导览／状态追问”意图；先识别明确编号，再按楼栋、指标、上下文消歧。未识别请求只给支持的示例，不做自由文本猜测。
2. **读取层**：仍从 `buildSnapshot()` 和现有 store 的只读投影取数。给工单、复查、模拟巡检补最小只读投影；不复制状态机或阈值计算。对象引用一律以当前数据库重读复核，避免缓存过期。
3. **计划层**：使用固定任务目录（上表六类）输出 `GuidePlan`：当前对象、步骤、预期页面、是否需确认、完成条件、下一步。计划只是界面状态，不是业务结果。
4. **执行层**：只读步骤通过现有 `buildLink()` 导航；演示写入通过扩展白名单，把命令映射到现有 `useDemoScenarioStore().load(key)`／`loadChain()`。不开放任意函数名、任意路由或自然语言生成 SQL。业务派工／验收／关闭继续交给原界面操作。
5. **会话层**：记录导览步骤和对象 ID。数据集重置时清空；对象已删除或状态变化时重新计算步骤。影像照片仍只在会话内；持久附件依旧走问题／工单入口。
6. **演示身份**：场景加载内部已有 `withActor()`，需要明确标“演示身份代入”；小瞳不能在常规问答里私自切身份。人工业务操作遵从当前身份权限。

建议把导览 UI 作为小组件接到现有 `AssistantPanel.vue`，避免继续加长面板文件。把固定任务元数据与命令执行器分开放置，遵守仓库 450 行文件、80 行函数、每层 8 文件的约束。

## 6. 一次演示的可见动线（约 5–7 分钟）

1. 演示者点悬浮小瞳，问“全校现在什么情况”；小瞳报真实本地统计，并打开驾驶舱。
2. 问“3号教学楼裂缝测点怎么样”；看板同一张卡、趋势和小瞳显示相同读数与采样时间。
3. 点“准备红色预警演示”并确认；红色强提醒出现，打开事件，核对规则和证据编号。
4. 问“为什么红／下一步怎么办”；小瞳解释证据并把人带到预警详情、问题与工单入口。
5. 点“带我看照片”；一键载入前后演示照片，框选比对；小瞳回答“疑似变化”的边界。
6. 点“演示巡检到点”；先用错 NFC 编号得到拒绝，再模拟正确编号到点，展开尝试历史。
7. 展示同一事件的派工、维修、验收、复查节点；由演示者在原业务界面完成需要责任人判断的动作，最后用小瞳复述实际完成状态与仍待事项。

| D 影像／模拟 NFC／业务闭环导览 | NFC 与业务主链已实测；影像框选、预设分析、小瞳复述已实测 | 修正演示照片与 8% 阈值不匹配的展示结果后复验 |

截至 2026-09-30 最新核验，**A、B 两组通过；C、D、E 三组部分通过**。E 组已从干净数据连续走过主线（见 §18.5），其影像步骤沿用 D 组的展示缺口：裂缝变化肉眼可见，却因像素差低于 8% 被判「未见明显差异」。先修演示素材／示范框选区域与既有阈值的匹配，再补验该步和全链最终核对。按五组统计是 **2 组通过、3 组部分通过**；不把这换算成模糊百分比，也不纳入服务端或真实硬件。

必须验证：同一事件 ID 贯穿红色提醒、看板、小瞳和问题详情；问答没有数据库副作用；取消确认零写入；重复载入不会额外建事件／问题／工单；失败停在当前步骤；影像差异不建预警；错 NFC 不到点；刷新／重载数据后旧上下文消失。运行相关测试、全量测试、类型检查、构建，最后浏览器连续走完一遍。

**小瞳联动。** 新增白名单导航目标（建议 `/campus?view=3d&b=<buildingId>&f=<floorId>&point=<pointId>`，最终参数名以路由实现为准）；打开前逐级核实 ID 与归属，不拼未经校验的 URL。问“B03 二层裂缝传感器在哪里”→ 消歧 → 打开 3D 并聚焦同一测点；点 3D 标记 → 小瞳沿用该点的 `AskContext.pointId` 解释当前读数/事件证据；问“红色预警在哪层”→ 按**真实事件**定位到楼层与标记，给出事件详情深链。只是定位和只读解释，绝不因 3D 颜色或动画重新计算等级/自动派工。数据集重置时清空选中对象，已归档或不存在的深链显示原因与返回 2D 地图入口。

**实现边界。** 先用本地程序化几何生成楼体、楼板、区域隔断与楼层标签，3D 只消费现有档案/快照；不将网上任意学校模型嵌入并冒称本校。Three.js 按需加载、标记用射线拾取、相机旋转缩放但限制进入模型；闲置时按需渲染并尊重减少动态效果。WebGL 不可用或窄屏性能不足时回退现有 2D 楼层图，原业务操作不中断。若日后引入 GLB，先校对比例、楼层分组、测点锚点和许可，再用 `GLTFLoader` 替换外观层，不改变业务 ID 映射。

### 15.1 模型表达与页面布局（实施规格）

**视觉语言。** 使用与现有产品一致的浅底、青蓝品牌色、清晰描边与少量柔和阴影，采用可读的低多边形建筑剖层图，不做霓虹科幻大屏、写实贴图或假摄像头画面。入口放在原「校园地图」页的「2D 平面／3D 楼层」双视图切换，默认仍是 2D。3D 主画布约占内容区 2/3，右侧约 1/3 是楼栋/楼层/测点事实卡；窄屏改为画布在上、事实卡在下。上方始终显示面包屑 `校园 > 楼栋 > 楼层 > 测点` 和「返回 2D」按钮。

**模型层级。** 校园视角采用约 35–45° 俯视的正交相机，4 栋按现有校园图相对位置排列。楼栋只需让人辨认 B03 教学楼、B01 综合楼、B02 实验楼、B04 体育馆四种体量，不暗示实测外立面。进入单栋后，可点击清晰的楼层按钮（不是只靠点 3D 表面）；所选层保留实体色，下方楼层半透明，上方楼层/屋顶淡出。竖向展开只沿 Y 轴轻移楼板，保证看得出层数；区域以低矮隔墙、地面色块和中文标签表达，不堆桌椅等没有档案依据的细节。体育馆用单层大跨空间，不复用教学楼的走廊房间模板。

**测点表达。** 传感器用圆形立体标记＋指标图标，人工检查点用菱形标记；选中点增加青蓝描边和引线。红/橙/黄只用于已有未关闭事件的等级，颜色旁必须同时有文字，灰色表示无有效数据或未建档，不能把“无事件”画成设备“在线”。选定楼层之外的标记隐藏；同层标记重叠时展开简短列表供选择。右侧事实卡来自现有只读选择器，优先显示测点编号、读数与采样时间、来源/质量、事件号，再列“查看趋势／预警详情／影像／问小瞳”。默认标签不超过 1–2 行，详细证据留在侧卡，避免 3D 画面被文字盖住。

**操作与动效。** 鼠标拖动旋转、滚轮缩放；触屏单指旋转、双指缩放。镜头在校园、楼栋、楼层、测点间做 250–350ms 的有方向过渡；`prefers-reduced-motion` 时直接切换。任何可点 3D 标记都必须在旁边的楼层/测点列表有等价原生按钮、可见焦点环和可读标签，避免键盘用户只能“点模型”。悬浮小瞳、红色强提醒及右侧事实卡不得互相遮挡，红色提醒仍保持最高层级。

### 15.2 代码框架与数据流（实施规格）

```text
src/core/spatial/
  layout.ts          # 2D/3D 共用的楼层区域布局描述；现有 FloorMap 不再私藏第二套房间几何
  project.ts         # Building/Floor/Point → 校园、楼层、标记的纯只读投影
  coordinates.ts     # 归一化坐标、楼层高度与世界坐标变换，含反向选择校验
  selection.ts       # 路由 query 解析、ID/归属核验与失效空态
src/components/map3d/
  Campus3DView.vue   # Vue 外壳：视图切换、响应式事实卡、WebGL/2D 回退
  SceneCanvas.vue    # Three renderer、相机、ResizeObserver、事件监听和资源释放
  buildGeometry.ts   # 4 类楼栋/每层楼板、墙体与区域的程序化模型
  markers.ts         # 传感器/人工检查点标记与 Raycaster 拾取
  FloorControls.vue  # 楼层列表、整栋/单层/展开按钮、无障碍替代操作
  SensorFacts.vue    # 复用只读快照与现有深链的事实卡
```

这只是职责边界，不要求一次创建所有文件；每层目录保持 ≤8 个文件、单文件尽量 ≤450 行、函数 ≤80 行。`CampusView.vue` 只接一个 2D/3D 切换与经校验的选中 ID，不塞 Three 场景构造代码；3D 包由 `import()` 在切入 3D 时才加载。`layout.ts` 是**唯一楼层布局**，现有 SVG `FloorMap` 与 3D 几何都消费它；在切换布局模板时，应先保证旧测点的归一化坐标映射和 2D 标记不漂移。若体育馆平面结构需要特殊模板，按建筑用途选模板，模板只决定示意隔断，不改变档案 ID 或测点坐标。

**坐标约定。** 统一世界轴 `X=楼层平面左右、Y=层高、Z=楼层平面上下`。测点局部位置由同一份 `Point.coord` 求得：`X=(coord.x-0.5)×示意楼板宽`、`Z=(coord.y-0.5)×示意楼板深`、`Y=楼层序号×演示层高+标记抬升`；实际实现须与共享 `layout.ts` 的边界保持一致，不能另选一套缩放值。整栋的 `Building.footprint` 只控制校园视图的中心/长宽比例/旋转，绝不作为施工米制尺寸。点击 3D 标记返回 `pointId`，再用现有 `buildingId/floorId` 校验，杜绝“模型上某个点看似在 B03，业务却打开 B01”的错链。

**单向数据流。** `archive + records + events + devices → 现有 assistant selectors/buildSnapshot → spatial.project（纯函数） → Vue 选中状态 → Three 场景`。路由 query 是选中对象的唯一可分享状态；相机角度和展开动画只是临时视图状态，不写 IndexedDB。3D 点击与小瞳定位都通过同一 `selectById` 路径；小瞳答卡只使用已经验证过的 `pointId/eventId` 生成白名单深链。业务数据变化时重算投影并只更新受影响的材质/标记，不重建整座校园场景；刷新或重载数据集后重新核验路由对象。

**渲染生命周期。** Three.js 使用正交相机、受限的 OrbitControls、Raycaster；画布按容器 `ResizeObserver` 调整大小，像素比上限 1.5，静止时按需渲染，少用动态阴影。切走 3D、数据集重置或组件卸载时销毁 renderer、controls、事件监听、几何体和材质；WebGL 初始化失败显示已有 2D 地图和明确提示。场景图形不走互联网实时下载，确保本机离线演示可用。外部 GLB 只能作为后续可替换的外观层，不能承载唯一的楼层/测点 ID。

**架构验收。** 纯函数测试覆盖 4 栋/8 层/8 点、B01/B02 缺档层、坐标边界、归档与错归属、路由消歧；浏览器测试覆盖 2D/3D 互切、B03 二层 4 个传感器的逐一聚焦、AI→3D→趋势/事件往返、键盘/触屏等价路径、900px 无溢出、减少动态效果和 WebGL 回退。重点判定是“同一 ID、同一读数和同一事件在 2D、3D、小瞳三处一致”，不以画面华丽程度代替数据正确性。

## 18. D 组影像复跑、E 组统一验收与三处发现（2026-09-30 凌晨）

**一句话结论。** 影像框选上轮"没做出来"的原因是**浏览器自动化产生不了"按下—拖动"手势**（工具限制），不是产品缺陷；补跑通过。E 组 5–7 分钟动线在独立源上从干净数据连续走通一遍：编号贯穿、取消零写入、问答零写入、重复载入幂等、数据集重置清上下文全部对上。另抓到并修掉两个真缺陷，记下三处待裁定项。

### 18.1 D 组影像支补完（§16 记的"未通过"解除，但口径要写清）

- **根因（实测）。** `cua.drag` 只派发 `pointermove`，**不派发 `pointerdown` / `pointerup`**；在页面上挂 window 级 capture 监听，整段拖拽期间 `pointerdown/pointerup/mousedown/mouseup` 一次都没有。`cua.click` 也没有任何事件到达页面（自派发一个 `pointerdown` 能被收到，证明监听有效）。所以上轮"两次拖拽都没落在前一张图上"是**工具能力问题**，`MediaComparePanel` 的指针处理链本身是对的。
- **复跑方式。** 用页面内派发的真实 `PointerEvent`（pointerdown → pointermove → pointerup）驱动**组件自身**的处理器，**产品代码一行未改**即得到框选：`框选：32% × 26%`、两张图都画出遮罩、分析按钮解禁；运行预设分析得到实测结论，小瞳只读复述同一结论（截图 `106-小瞳影像复述-未见明显差异6%.png`）。
- **必须写明的边界。** 这一步的"手势"不是真实指针输入，属**处理器级实测**；DOM 点击（`.click()`）触发的按钮路径是真实的。把指针链写成"已实测通过"与事实不符。
- 顺带确认一处既有行为是对的：框选区域取**最后一次 `pointermove`**（`onPointerUp` 只做可用性判定），所以只派发一个中间点时界面回显 `4% × 4%` 是正确的，不是缺陷。

### 18.2 演示照片对与阈值不匹配（新发现，本轮**未改**）

实测（480 长边、像素差 ≥ 18，与产品同一套口径）：`corridor-crack-before.png` 与 `corridor-crack-after.png` 全图变化像素占比 **0.4%**；对各类框做穷举，**最好的框只有 6.0%**，而阈值是 8%。界面实际回显："框选：8% × 8%｜差异像素占比 6.0%｜**未见明显差异**"。

也就是说：**用当前这组图和当前阈值，"疑似变化"演示不出来**，而 §6 第 5 步写的正是"小瞳回答'疑似变化'的边界"。根因是裂缝在画面里是**细线**，面积占比天然很小，8% 的面积阈值对局部缺陷系统性不敏感。

两种修法（都会改到面向观众的结论或素材，故不擅自决定）：

1. 让生成的 after 图变化更明显（裂缝加宽/延伸）——素材本就是"生成演示图"，**阈值不用动**；
2. 下调 `DEFAULT_COMPARE_OPTIONS.changedRatio`（例如 8% → 3%）——属演示口径调整，现有素材可过，但更松的阈值也更容易被无关变化触发。

`public/demo-media/*.png` **未纳入版本控制、没有 git 历史可回退**，这也在"不擅自动素材"的理由里。

### 18.3 修掉的真缺陷：导览卡「核对并准备巡检演示数据」是死键

- **现象。** 点击无任何反应：不弹确认框、不写库。

## 22. §21 追加：测点贴墙安装、按楼栋建模与外部体量（2026-09-30 用户反馈驱动）

**触发。** 用户看 3D 后连提四条：① 传感器应该**附着在墙面或具体物件上**（当时是浮在房间中央的柱子）；② 3D 入口应该**是一栋楼的建模**，右边选楼层看该层传感器在哪；③ 建筑**不在视图中央**、不能随意放大与 360° 旋转；④ **点击传感器要显示实时信息**。随后两条补充：⑤ 右侧首先应是**校园总览**；⑥ 校园总览要能**看到四栋在校园里与 2D 对应的位置 + 建筑的外部模型**。

**检索（按用户要求走了 Exa，共 237 条来源、三路子问题）。** 关键结论与出处：

| 结论 | 出处 |
| --- | --- |
| 程序化建筑**不要靠射线找墙面**：直接按"墙段 + 法线 + 安装高度"算 `P0 + d·along + up·h + n·(halfDepth+ε)` | [surface-query.ts](https://github.com/pascalorg/editor/blob/main/packages/nodes/src/measurement/surface-query.ts)、[anchors.ts](https://github.com/eldinor/lite-instancer/blob/main/packages/annotator/src/anchors.ts) |
| 设备要按"半厚 + ε"外推，姿态用 `setFromUnitVectors` 把 +Z 对到法线；共面底板用 `polygonOffset` | [three.js：法线放置](https://github.com/google/xrblocks/blob/main/src/utils/ObjectPlacement.ts)、[z-fighting 处理](https://discourse.threejs.org/t/mesh-on-top-of-another-remove-overlapping-render-order/15261) |
| 引线**不能贴墙画**（`polygonOffset` 对 `Line` 无效），要先沿法线伸出墙外 | [three.js：线的 z-fighting](https://discourse.threejs.org/t/how-to-fix-z-fighting-of-lines/53510) |
| 挂载语义：`IfcLocalPlacement.PlacementRelTo` 是"挂到宿主构件"的机制；传感器缺"挂哪面墙"这个字段时需**按位置派生**宿主面 | [IFC4.3 局部放置](https://buildingsmart.or.kr/newsfile/ifc4_3/HTML/concepts/Product_Shape/Product_Placement/Product_Local_Placement/content.html)、[scan-to-BIM 宿主派生](https://isprs-archives.copernicus.org/articles/XLVI-5-W1-2022/109/2022/isprs-archives-XLVI-5-W1-2022-109-2022.pdf) |
| 安装高度惯例：房间类仪器 1.2–1.5 m AFF；裂缝计/倾角计靠近构件根部 0.3–0.6 m；加速度计靠节点 | UFGS / ADA 308 可达范围、GEOKON 裂缝计与倾角计手册（本轮未取得稳定公开链接，按惯例取用） |
| 楼层列表当主导航、**"变淡"而不是"隐藏"**、空楼层保留可选中并显示 0 | [Bentley 楼层选择器](https://docs.bentley.com/LiveContent/web/OpenBuildings%20Designer%20Help-v5/en/FloorSelector.html)、[三维隔离的 UX 研究](https://tingtingchuang.com/ux-case-studies/making-3d-usable-ooux-finding-from-isolate-highlight-features/) |
| "没有数据"不能看起来像"正常"：离线/无数据要**去饱和**并与正常态区分 | [three.js 数字孪生界面](https://www.intelligentgraphicandcode.com/development/threejs-interfaces/digital-twins) |

**改了什么。**

1. **墙面成为一等公民（`core/spatial/layout.ts`）。** 新增 `WallFace`（区域框的一条边 + 指向区域内部的单位法线）与 `mountOnWall()`：只在"点位在墙内侧且垂足落在墙段内"的墙面里取最近的一面，取不到就**如实回落**（`inside/withinSpan` 为假、或距离超过 90 内容单位）——不硬把测点按到别的房间的墙上。
2. **贴墙安装写进投影（`core/spatial/project.ts`）而非渲染层。** `PointMarker` 现在带 `mount`（墙所在区域、垂足、距离、法线）与 `mountHeight`；高度按指标类型取（裂缝 0.55 / 倾角 0.65 / 振动 0.8 / 温湿度 1.55 / 人工点 1.45 m），口径与出处写在 `coordinates.mountHeightOf` 上。这样"装在哪、多高"是**数据**，场景只负责画。
3. **设备几何重做（`sceneParts.ts`）。** 底座（共面底板带 `polygonOffset`）→ 支架 → 机身（事件等级着色）→ 面板 → 沿法线伸出的引杆 → 编号贴片；整组用 `setFromUnitVectors` 把局部 +Z 对到墙面法线，**换任何朝向的墙都不用改**；底座按半厚 + 0.1 外推，这一项就是"贴住"与"悬浮"的分界。
4. **内部视图：当前层满高墙（2.8）+ 其余层矮墙（0.5）**，传感器才有真实的墙面可贴；**仅本层模式把其余层画成 16% 透明度的"幽灵楼板"**而不是直接隐藏（隔离用变淡，保留整栋方位的上下文）。
5. **取景改为量真实包围盒（`sceneBuild.frameContent`）。** 目标点 = 内容包围盒中心、视口半高 = `max(高度, 平面跨度/宽高比) × 0.72` —— 之前用公式估尺寸，宽屏画布把建筑缩成一小块、且目标点取的是"楼栋平面中心"而不是内容中心，这就是"建筑一直不在视图中央"的根因。
6. **自由缩放与旋转。** `minPolarAngle 0.02 / maxPolarAngle π-0.02`（近乎俯视到近乎平视，水平方向本来就是整圈）、`minZoom 0.15 / maxZoom 8`。

8. **点击设备必中。** 拾取会**沿父链**找带 `pointId` 的节点（点到底座/支架/面板/引杆/编号任一处都算），并给每台设备套一个 `opacity: 0` 的**拾取代理球**（半径 1.25），补偿设备本体只有二十来像素的问题。

### 22.1 追加：「建模不在界面中间」的两个真实根因（2026-09-30）

用户又报了一次"建模始终不在该展示界面的中间"。**实测数据**（临时 hook 打印画布与投影）：画布 `attr/style = 945×596`，而它的容器 `.scene` 只有 `632×399` —— **canvas 比容器大，被裁掉右侧与下方**；画面是按画布中心（945×596）摆的，所以"可见区域"的几何跑到右下角。两个叠加的根因：

1. **`renderer.setSize(w, h, false)` 不改 CSS 尺寸。** 我在 resize 时传了 `false`（"别动样式，我自己用 CSS 控制"），但 canvas 元素本身没有 CSS 规则，于是它的 CSS 尺寸停在**属性值**上 —— 而这个属性值是布局**变窄之前**的旧尺寸。窗口布局一变（右侧事实卡出现、窗口缩小），画布就比容器大。改为 `setSize(w, h, true)`（同时写 style），并在组件里给 `canvas { display: block }`、容器加 `overflow: hidden`。
2. **取景包围盒把文字贴片也算进去了。** 楼栋名、区域名、测点编号都是 Sprite，挂在楼顶上方还带引杆，`Box3.setFromObject(root)` 会把它们算进内容范围，于是"几何中心"被这些标签往上拖，真实楼体被压到画面下方。改为**只遍历网格、跳过 Sprite**（`contentBox()` 里 `if (child.isSprite) return`）—— 标签按需显示即可，不该参与取景。

修完后实测：canvas `630×397` ≈ 容器 `632×399` ✓、内容中心投影 `centerNdc = [0, 0]` ✓、截图里楼体居中（`118-3D-取景居中.png`）。`npm test` 840 项 / 74 文件、typecheck、build 全过；`sceneBuild.ts` 清理临时 hook 后 215 行。

### 22.2 追加：独立的「校园 3D」档位（2026-09-30）

用户反馈：**"还是没有给出校园这几个完整建筑的建模，只有每个建筑的每个楼层的建模；要单独列出一个选项是校园 3D 来展示外观模型，位置摆放一定要和 2D 平面一致。"**

**问题定位。** 上一轮虽然做了外部体量模型（`sceneShell.ts`），但它只藏在面板里的「回到校园视图」后面 —— 而 3D 的入口默认**直接进单栋**，所以从界面上根本进不到"看四栋外观"这一档。而且切换到校园档时面板已经按旧值挂载，`buildingId` 还留在上一栋（实测过：hash 写成 `view=3d`，画面却仍是 B03 的楼层剖面）。

**改法。**

1. **视图开关从两档变三档**：`2D 平面` ／ **`校园 3D`** ／ `3D 楼层`。三档与链接一一对应：
   - `#/campus`（或 `?b=`）→ 2D 平面；
   - `#/campus?view=3d`（**不带楼栋**）→ 校园 3D，四栋完整外观，位置按 `footprint` 与 2D 校园图一一对应；
   - `#/campus?view=3d&b=&f=&point=` → 3D 楼层，进单栋看逐层剖面与贴墙传感器。
2. **档位判定下沉为纯函数** `stageOf(target)`：`view!=3d → '2d'`、`view=3d 且无楼栋 → 'campus'`、`view=3d 且有楼栋 → 'building'`。有单测（含"校园 3D 的链接不写楼栋参数"）。
3. **面板增加 `stage` 入参并 watch 它**：切到校园档时主动清空楼栋/楼层/测点；切到楼层档时落到父级给的那一栋（没有就用第一栋）。`setView` 里也改成**先备好初始选择再切档位** —— 面板是 `v-if` 挂载的，顺序反了会先按旧值挂上去。
4. 校园 3D 的卡片标题/副标题单独写：标题「校园 3D」、副标题说明"四栋建筑的完整外观模型，位置按楼栋档案的校园占位摆放，与 2D 校园图一一对应；点楼栋进入楼层视图"。点模型进入单栋的拾取沿用同一条链路（外壳整组带 `kind='building'` + `buildingId`）。

**实测（独立源，选项卡逐档切换）。** 校园 3D → hash `#/campus?view=3d`、面包屑"校园"、画面四栋（B01/B02 在上、B03/B04 在下，与 2D 校园图的占位一致，截图 `119`/`120` 对照）→ 切「3D 楼层」→ hash `#/campus?view=3d&b=bld_b01`、面包屑 `校园 › B01 1号综合楼 › 一层` → 切「2D 平面」→ hash `#/campus?b=bld_b01`、2D 校园图回来 → 再切回校园 3D 仍然正确。全程无控制台报错。

`npm test` **842 项 / 74 文件**全过（新增 2 条档位与链接口径用例）；typecheck 零错误；build 通过；规模只剩三处既有超标。

## 25. 小瞳 × 3D 空间讲解设计依据（2026-09-30，第一批已实施，第二批待选）

**现有基线。** 测点和事件回答带 `spatial_3d` 白名单深链，按楼栋/楼层/测点 ID 进入 3D；页面逐级校验归属，选中墙面测点后展示与小瞳同源的最近有效读数、采样/录入时间、来源、人工登记设备状态和未关闭事件。3D 事实卡的「问小瞳」又把当前 `pointId` 送回问答。现有相机只在范围、楼栋、视图、楼层变化时取景，选中测点不会重设用户视角。当前**没有**自然语言运镜、历史回放、场景内影像叠层或反事实推演。

**设计目标。** 小瞳作为「空间讲解员」，把自然语言解析成受控的只读 `SceneIntent`，让半屏问答与半屏 3D 对准同一个对象。`SceneIntent` 只允许 `focusBuilding / isolateFloor / focusPoint / showEventEvidence / resetView` 五类展示动作；解析测点与事件后复用现有 ID、`resolveSpatialSelection`、`buildSnapshot` 与业务规则。3D 只接收展示指令，不自行生成读数、阈值、预警或业务结论。

**第一批（演示优先）。** ① 问「3 号教学楼二层裂缝点在哪」后先给事实和定位按钮，用户点击才镜头平滑聚焦 B03→二层→墙面测点；提供暂停/重置，减少动态效果时即时定位。② 3D 中点测点，小瞳自动带 `pointId` 上下文；问「为什么红」时展开同一事件的采样值、规则版本和证据编号，镜头与证据卡一起对准该点。③ 加「90 秒讲解」：校园四栋→楼栋→楼层→墙面测点→趋势/事件/影像→原业务处置页；播放只控制页面、镜头与只读卡，准备演示数据仍要人工确认，派工/验收/复查/关闭仍在原表单由人决定。

**第二批（有余量再做）。** ④ 「证据时光轴」按事件已保存证据逐条回放，明确显示采样时间与录入时间，历史补录加标识；不假装实时传输。⑤ 「空间证据抽屉」把已有问题/工单正式附件与影像页会话比对并列展示，后者标明刷新即失、预设像素差异不是裂缝宽度。⑥ 「假设沙盘」可输入假设读数调用现有纯规则判定，3D 用虚线/紫色明确标为模拟，不写记录、不生成事件、不替代现场判断。若时间不足，优先①②③，④⑤⑥不列为本轮验收条件。

**验收与边界。** 2D/3D/小瞳/预警详情对同一 ID、读数、时间、来源一致；错 ID、归档或跨楼层目标给原因且不飞向错误测点；普通提问与镜头讲解前后 IndexedDB 不变；红色只来自既有未关闭事件；没有设备心跳就不说「在线/实时」；演示回放与真实采样明确区分；键盘可暂停与重置，窄屏可用。预期一轮交付第一批、第二轮只补稳定性与可选增强。

## 30. 红色事件演示减负方案（设计稿，尚未实施）

**界面减负。** 红色事件导览时收起通用的影像/NFC 模块到「扩展展示」，主卡只留进度、证据速览、下一责任角色和一个主按钮。导航到业务页后小瞳收成窄条，避免和右侧抽屉相互遮挡；返回时显式重读事件、问题、工单、复查阶段，继续显示同一事件 ID。窄条给「返回导览」与「结束」两个入口；Esc 关闭并按既有焦点回位规则处理。原七阶段状态机与写入仓储、权限、回滚逻辑一字不改；三幕只是其只读投影。

### 22.3 追加：看板点卡片 → 下方趋势图跟随（2026-09-30）

用户要求：**点传感器状态卡片时，下面的图像也切到那个传感器。**

**原因**：卡墙（`SensorCardWall`）只负责展示，趋势图（`ReadingTrendChart`）按"① 指标类型"这个**维度筛选**选测点 —— 两边没连上。而且趋势图的测点叠加列表里，`chartPoints` 会先按 `chartMetric` 过滤，所以**换指标类别的传感器（例如从裂缝切到倾角）光勾选也画不出来**，必须同时把维度也切过去。

**改法**（都在前端展示层，不碰判定与写库）：
- `SensorCardWall` 增加 `focusedPointId` 入参与 `focus` 事件；卡片本体可点、可键盘（Enter/Space 显式处理）、`aria-pressed` 标注，聚焦态加高亮；卡片内的「看趋势／在地图上定位／打开事件」三个链接加 `@click.stop`，不误触聚焦。
- `DashboardView` 增加 `focusedPointId`：聚焦时**趋势图的维度跟着切到这个测点自己的指标**（单位、数值维度、三级阈值线一起走），并把"③ 测点叠加"收成它一个；顶部出现一条提示条写明"下面的趋势图正画着它"，并给「取消聚焦」。
- **同一张卡片再点一次即取消**；改动楼栋/楼层/指标筛选、或点「全选测点」也会取消聚焦 —— 否则图会停在一个已被筛掉、卡片也看不见的测点上。
- 点卡片会把趋势图滚进视野（`nextTick` + `scrollIntoView`），现场不用手动往下拉。

**实测（独立源，1440 宽）**：默认维度 `裂缝开合 · 裂缝宽度（mm）` → 点 `B03-F2-TILT01` 卡片 → 提示条出现、① 指标类型高亮**倾角变化**、② 数值维度自动落到 **X 轴角度**、③ 只勾住 TILT01、图例与"当前维度：倾角变化 · X 轴角度（°）｜测点 1 个"一致；再点同一张卡 → 回到 `裂缝开合 · 裂缝宽度（mm）`、提示条消失、高亮清零。截图 `121-看板-点卡片切换下方趋势图.png`。

`npm test` **859 项 / 78 文件**全过（并行会话本轮又补了 17 条测试）；typecheck、build 通过。

**22.3.1 追加：指标类型按钮再点一次 = 回到综合。** 用户要求"重复点击指标类型会回到综合的传感器状态卡片界面"。原实现里点该按钮只会**重新选中同一个指标**，退不回去。改成切换语义（`pickMetric`）：点**正在显示的那个**指标 → 清掉指标筛选与卡墙聚焦，卡墙重新显示全部传感器。

判定用 `chartMetric`（当前实际画着的指标）而不是筛选值本身 —— 因为**卡墙聚焦时高亮的也是它**，用户眼里的"当前指标"才是他要点掉的那个。所以两条路径都能回到综合：① 指标筛选后再点同一按钮；② 从卡墙聚焦后再点同一指标。

### 22.4 追加：小瞳面板自动跟随最新一轮对话（2026-09-30）

用户要求："每次和 AI 对话时界面都要到最下面，能看见新对话的对话过程。"

**行为**：每次提问（新增一轮）或回答落地，把**最新一轮的顶边对齐到滚动容器顶部**（约 8px），所以新问答从问题行、结论、数值开始就可见。实测五轮问答都落在顶边 8–12px、可见 98–100%。

**三个坑（都实测过，记下来免得重复踩）**：

1. **不能只盯 `turns.length`**：`ask()` 是**先插入提问那一轮**、再异步回填答案，轮数不变。要盯的是"最后一轮的 `id` + 是否已有结果"，所以引入了 `latestKey` 计算属性。
2. **`.turn` 在面板里不止一层**：答案卡自己的根元素也叫 `turn`（`ARTICLE.turn`）。用 `querySelectorAll('.turn')` 取"文档顺序最后一个"会拿到别的轮次里的嵌套元素，算出的目标位置被夹回 0 —— 换成**只认 `.body` 的直接子元素**才对。
3. **回答落地后内容还会继续长高**：事实卡、趋势小图、以及**异步重读的阶段卡**都是渲染完才撑开高度。只对齐一次等于算在"还没长起来"的那一刻（实测那一刻最新一轮顶边还在 0 附近，长完就掉到 700 以下）。所以对齐要**反复做**：每 250ms 一次、最多 10 次，且**必须"顶边就位 + 连续两次高度不变"才算稳定**——只看"两次算出的目标相同"会误判（内容还没长，两次当然一样）。
4. **不要用平滑滚动做这件事**：布局持续变化时平滑动画会被打断在半路，表现出来就是"滚了等于没滚"。瞬时赋值（`scrollTop = …`）反而稳定，也顺带满足"减少动态效果"。导览卡自己的"回顶部"保留平滑。
5. `overflow-anchor: none` 加在滚动容器上：**它不是本次的修复**（排查时试过，改动前后现象一样），而是护栏 —— 面板的滚动位置由我们自己接管，不要让浏览器在内容插入时再按它的锚定策略改一次。

**保留的旧行为**：进入导览时"回顶部看阶段卡"只在该次更新**没有新问答**时生效（实际几乎不会触发，因为导览都由提问唤起）；刚问完时以"看得见新回答"为准，阶段卡向上滚一点即可看到 —— 这是按用户这次的要求定的优先级。

验证：`npm test` 861 项 / 79 文件全过；typecheck、build 通过。浏览器实测五轮（含导览切换那次）最新一轮顶边 8–12px。

## 36. 小瞳主导的影像对比联动（已于 2026-09-30 实施，记录见 §37）

**用户目标。** 影像对比直接进入演示级 AI 的回答与操作流，减少进入影像页、选图、框选、返回提问的步骤。本节细化 §34，已于 2026-09-30 按此实施（§37）；真实公开底图与模拟派生图的来源标签继续保留。

**一条演示动线。** 设置页唯一全链入口准备业务数据及视觉演示场景的就绪标记；小瞳在测点上下文中收到“看看这面墙的变化”后，读取同一测点记录/事件，按已准备的场景读取本地照片进入会话，使用该素材登记的区域运行现有像素差异分析，然后在回答中展示数字、趋势、照片与结果。图片可延迟解码以避免全链载入过重。该问答过程不新增业务记录、不补建示例校区、不替人提交结论；未准备场景时明确提示到设置页准备，保留手选会话照片能力。

**对象与优先级。** pointId 是问答、3D 与影像之间的关联键。明确选择的当前会话照片对优先；缺少会话对时，已准备的内置视觉演示场景可作为后备，必须提示使用内置素材。指代问题沿用已明确选中的测点；多个测点或多个照片对时先显示候选，不借用别的测点照片。公开实拍派生对仅为该测点的演示关联，不能声称拍摄于其校园墙面。

**半屏内交互。** 顶部一句话回答；其下当前读数/历史峰值、迷你趋势、照片对和差异摘要。回答内提供“对比裂缝区域”“对比完好墙面”两个快捷操作，各自使用登记的区域实时计算，辅助说明变化与控制区域；“自己框选”展开同一卡片内的交互，不强迫跳页。点击照片打开同面板放大视图，支持同步缩放；拖动前后滑杆查看同底图差异。完整影像页只承接高级操作。

**小瞳表现。** 本地流程显示“读取监测记录 → 核对关联影像 → 计算区域差异 → 整理结果”，每一步由真实任务完成状态驱动，禁止伪装联网或显示虚构识别准确率。现有分段呈现复用，结论先出、图表和照片随后出；提供“立即显示全部”。预设区域边框和扫描动效属于展示辅助，人工预设裂缝区域不得被称为模型自动识别。减少动态效果时直接显示静态结果。

**连续问答。** 支持固定示例“这面墙有什么变化”“把变化区域放大”“完好墙面也变了吗”“对应哪个传感器”“带我到 3D 看位置”“为什么触发红色”“读数恢复了吗”。放大/区域切换/3D 导航都是会话或展示操作；确认式业务写入仍沿用既有指令权限与确认机制。首先核对已有问法解析和动作白名单，按需扩展，避免重新实现一个通用代理框架。

**结果与来源。** 每次结果绑定 pointId、前后照片 ID、各自来源、真实或模拟时间、区域、比对时间、方法及计算参数。当前值与历史峰值分开取数，毫米来自记录，像素占比来自图像。区域切换后更新影像部分，不让旧结果套新照片；修改/删除照片后旧结果标失效。刷新会话后旧答案的照片预览显示已失效，必须由新提问明确重新载入已准备的内置场景，不能在渲染旧答案时静默偷换照片。

**3D 联动。** 影像卡“3D 定位”沿现有白名单深链定位同一 pointId，打开楼栋/楼层并突出该测点；可以附带“视觉演示素材关联于此测点”的说明。没有实测影像到模型配准时，不把照片像素区域映射成 3D 墙面裂缝、不自动生成裂缝几何体。用户从 3D 的“问小瞳”进入时，上下文沿用选中测点，半屏展示同一照片场景。

**开发顺序与属主建议。** 一个开发批次、一次统一验收。素材线负责公开原图许可核对、模拟派生图与区域元数据；问答线负责多预览及视觉问法/上下文/只读组合；界面线负责照片框、控制区切换、放大滑杆和 3D 导航。共享 types、media store、会话和 AppShell 由单一属主集成，避免并行覆盖。首批优先做自动取同测点素材、同屏趋势与照片、两区域对比及 3D 定位；滑杆和复杂动效属于第二优先级，不阻塞首批交付。

**统一验收。** 从设置页唯一入口准备后，一次提问显示同测点的数字/趋势/照片；裂缝区域和控制区域使用各自实际计算结果；切测点不串图；当前值与历史峰值不混；单张图、不可比对与数据/影像不一致均如实显示；3D 到同一测点；刷新后旧预览失效；问答前后业务表无变化；900px 和 Tab/Enter/Esc 可操作。通过后重跑全量测试/typecheck/build并更新来源、截图及真实剩余项。

**下一步工程师提示词。** 按 §34/36 实施“在小瞳半屏里完成视觉对比”。不要先要求用户去影像页操作：设置页唯一全链入口准备视觉演示场景，提问后按同 pointId 读取已准备的本地素材并运行现有区域像素差异算法；优先使用用户已选会话照片对。扩展多预览，复用已有趋势和照片组件，内嵌裂缝区/控制区对比、放大、3D 定位；实际区域差异计算不得硬编码32.7%。真实底图与模拟派生图明确标注，当前值和历史峰值分别读取。所有业务问答保持零写库，无外部API、无摄像头；刷新后旧预览失效，重新提问可明确重新载入准备好的场景。三个并行工作线先划清共享文件属主，最后一次统一浏览器验收与命令验证，更新本方案和上下文。

**剩余量。** 本轮属于设计细化，尚未交付视觉联动增强。按上述首批优先级剩一个开发批次及一次统一验收；最终全系统5–7分钟跨页演示仍需结合该增强重跑，不按对话轮数或未经核验的百分比声称已完成。


## 37. 小瞳视觉巡检联动（已实施，2026-09-30）

§34/§36 的设计在本节落地：**一次提问就在半屏里看完整条证据链**，不再要求用户先去影像页选图、框选、再回来问。影像页仍是高级入口（自框选、留存到附件），但它不再是必经之路。

**交付效果（实测）。** 设置页唯一入口载入全链（13 个场景，含新增的「视觉证据素材」）后，问「这面墙的裂缝有什么变化？给我看证据」，半屏内依次出现：测点编号与来源徽标 → 当前有效读数 0.53 mm（记录 R20260930-004，采样 2026-09-30 21:36，处于近 30 分钟内）→ 历史峰值（事件证据，不是当前值）0.82 mm（E20260918-001，证据记录 R20260920-001）→ 关联事件状态「恢复待确认」→ 迷你趋势 → 前后两张证据影像（同一块登记裂缝区框）→ 区域差异（登记裂缝区 15.1% 疑似变化 / 完好墙面 0.0% 未见明显差异，含比对时间、绑定对象与区域坐标）→ 底部「3D 定位 / 预警依据 / 完整影像对比」。

### A 线：证据素材

- **保留公开实拍原图** `public/demo-media/commons-crack-example.jpg`，来源、作者与许可随包记录（CC0 1.0，作者 booledozer，Wikimedia Commons）。核对时 Commons 文件页连接超时，许可按工程既有记录沿用，**未再向外部二次确认**，这点如实写在报告里。
- **新增同底图模拟变化图** `commons-crack-evidence-simulated.jpg`（同尺寸 960×720、同裁切）：只把**登记裂缝区**内的裂缝加宽变深（手工描出的路径 + 遮罩模糊，避免块状痕迹），控制区一个像素都没动。
- **素材级实测**（`tests/media/evidenceMaterials.test.ts`，直读真实 JPEG，与页面同一套亮度口径）：裂缝区 15.0% 判**疑似变化**（阈值 8%，余量 ≥1.5 倍）；完好墙面 0.0% 判**未见明显差异**；整图直比判未见明显差异（守住"框选"这个动作的意义）；**登记区域外没有任何达到阈值的像素差**（区域外最大亮度差 < 5，只剩 JPEG 重编码的量化噪声）。
- 页面内实际算出的 15.1% 与测试里的 15.0% 略有差异：canvas 缩放与盒式平均不是同一个实现。**两个数都来自真实像素**，没有硬编码（设计方案里担心的"沿用 32.7%"没有出现）。

### B 线：多预览与视觉问法

- **一次迁移**：`AskResult.preview: AskPreview | null` → `previews: AskPreview[]`，同步改草稿类型、两个生产者（测点 / 影像）、分段判断、渲染与既有测试；没有留下 `preview`/`previews` 两套接口。
- **新预览种类 `visual_evidence`**：把测点头部、两张数值卡、关联事件、迷你趋势、照片对（含登记区域框）、区域结果与三个去向放进同一段；趋势与照片仍复用既有组件（`PointTrendPreview`、`MediaPairPreview`）。
- **组合纯函数** `src/assistant/linkage/compose.ts`：当前有效读数与**历史峰值分列** —— 峰值取事件证据**记录**里的同字段最大值（不是判定值 0.32 mm，更不是当前值），事件等级与状态直接引用事件本体，**不重算阈值、不改事件状态**。
- **编排** `src/assistant/linkage/run.ts`：先看当前会话影像；一对都凑不出且设置页那条场景已就绪时**按需读取**内置素材（只进会话、不写库）；再用 `src/core/media/analysis.ts`（与影像页「运行预设分析」同一个计算入口）算登记裂缝区、完好墙面与自框区。
- **八条演示问法**全部落地（`parse.ts` 的确定性规则，未引入通用代理）：「这面墙的裂缝有什么变化？」「给我看数据和照片。」「放大变化区域。」「完好墙面也变了吗？」「对应哪个传感器？」「带我到 3D 看位置。」「为什么触发红色？」「读数恢复了吗？」。其中"读数恢复"只引用最新有效读数、事件证据峰值与证据里记下的阈值快照，并明确写出"恢复待确认不等于可以关闭"。
- 问句没有线索、也没有上下文时，按**当前会话影像所属测点**回答并把这条口径写进回答；多个测点都有影像时先给候选，不挑一个。

### C 线：半屏交互与呈现

- 照片卡四个操作：**看裂缝区域 / 看完好墙面**（各自用登记区域实时重算）/ **放大对比**（1×→2×→3×，两张图共用同一个原点，实测两张的 `matrix(2,0,0,2,0,0)` 与 `transform-origin` 完全一致）/ **自己框选**（在照片上拖框，归一化坐标，松手即算）。
- **就地更新**：区域切换改的是**同一条回答**（`session.applyVisual`），实测点「看完好墙面」后轮数不变、框与结论一起变、提示「在这条回答里更新，没有新增一轮」。
- **分段呈现**：视觉问法显示「读取监测记录 → 核对关联影像 → 计算区域差异 → 整理结果」四步，进度由编排在**每步真正做完之后**上报（`AskStage`），界面显示不会跑到真实完成度前面；每处都给「立即显示全部」；减少动态效果时直接出结果。
- 口径与边界：没有"自动识别裂缝"、没有识别准确率、没有联网字样；预设区域一律写「人工预设的示范区域」；照片说明写「基于实拍素材的变化演示，非真实连续拍摄」。

### 现场交互：一次启动，按任务补缺，沿同一对象演示

1. 在设置页原卡中选择“本次演示允许自动补齐临时数据”，仍点唯一的“一键载入全链演示数据”。载入范围和自动补齐范围同卡说明，不增加小瞳确认准备按钮或各模块导入按钮。
2. 初次生成成功后建立内存演示会话，绑定数据集版本/重置代次和本次演示ID；全链部分失败则只开放已经验证可用的能力，不标全部就绪。
3. 说“带我演示B03-F2-CRACK01的裂缝变化”，编排层先重读实际记录、素材、事件与关联对象，确定当前同一测点的准备缺项。
4. 已有可用对象直接使用；只缺允许补齐的演示数据时，经统一准备服务补最小缺项，显示实际过程：“检查目标 → 补齐缺项 → 核验结果 → 打开证据”。失败如实显示原因，不继续依赖失败步骤。
5. 重读快照后调用既有只读问答。半屏呈现当前值/历史峰值/趋势/影像，定位3D同一测点；复用现有GuideCard呈现本幕单个主要动作。
6. 人在原表单办理派工、接单、验收、复查或关闭后，返回小瞳即重读实际阶段，再给下一幕。历史回看与现场待办分清，不把已验收工单重置成待派工。
7. 收尾显示实际对象对账单；清空数据、重载示例、恢复备份、刷新页面或退出本次演示均撤销自动补齐会话，重新启动仍回唯一设置入口。

普通查询继续走askZhutong，只读无写入；自动补齐由显式“演示任务”编排层调用，不能在selectors/answers内部偷写。进入演示会话后，通过演示问法或现有导览进入任务不需每次确认。没有会话时只给原设置页导航。

### 更能帮助演示的四个补充

- **目标跟随**：本次任务固定pointId；event/issue/order/media pair均从真实关联解析。多候选先让人选择，不能从另一个测点借图或把不同案例拼成同一链。看板筛选、3D楼栋/楼层/测点与小瞳上下文通过已有白名单导航同步。

- **下一幕预热**：在当前幕展示期间，只读检查下一幕条件并预读/解码已登记的本地影像，缩短页面切换和图片等待；预热不触发业务写入，缺数据仍等到进入该演示任务后才按白名单补齐。
- **演示对账单**：新增/复用/跳过/失败分列，列事件号、记录证据、问题号、工单号、模拟NFC状态与影像来源。对账是本次请求对象集合，不用全库总数；expected字符串只展示，正式校验用结构化条件和原关联/一致性检查。影像结果必须实际计算，当前与峰值分列，不能写死15.1%。

### 统一提问处理顺序

提问→拆任务/对象/范围/时间/材料→验证真实上下文→必要时补一个关键选择→分流只读查询、明确分析/准备任务、导航或原人办表单→按同对象数据答题→生成相关追问。

1. **对象解析**：明确编号/唯一名称优先；点卡或详情入口带实际对象；“当前选中的”用页面明确选中对象；“刚才那个”用最近已回答对象。“它/这里/这面墙”如页面与上一回答不一致则给两个具名候选，不偷换对象。无选择的首页按全校范围，不默认某个测点。上下文只含页面路由、selection/event/issue/order、photoPair/video/frame/region、读取时刻/数据集代次，不读取用户摄像头或任意页面截图。
2. **范围/时间**：独立识别楼栋、楼层、区域、指标/字段、指定对象列表；时间区分最新有效值、事件触发时值、历史峰值、明确时间段、视频片内秒数。缺时间时状态默认最新有效、原因用所选事件证据并注明；“全校异常”默认未关闭事件，先说明范围，不与设备心跳故障混为一谈。
3. **任务分类**：概况/状态、追因解释、数值趋势对比、照片对比/区域操作、视频播放/抽帧/对比、3D导航、办理进度、准备补齐、能力帮助分别有目标和最小结果。“怎么上传照片”是帮助，“分析已有照片”不准备缺失素材，“不要补数据”是否定写入约束；授权不等于任何问句都允许写。普通查询不写库；明确准备/分析任务仍走原授权队列。
4. **最小补问**：有唯一对象和默认合理范围就直接回答；多对象给具名卡片（楼栋/楼层/指标/状态），保留原问句/操作/时间，点候选后继续，不让用户重打。无材料时说明缺哪一项，给同页原入口；未授权可导航唯一Settings，不新建载入按钮。对象选定后还缺照片对才继续材料选择，不能一次要求填写所有字段。
5. **组合请求**：如“读数多少，照片有没有变化”只组合两个需要的只读/分析结果，共用同point、各自时间与来源；读取与导航按依赖顺序，准备必须单独判授权，业务提交仍原表单。缺其中一项可给已有结果并清楚列缺项，不拿别点素材补齐。两个传感器比较须解析两对象且同字段/单位，跨单位给并列事实而非共同阈值或硬排大小。
6. **答案与追问**：先回答当前问题一句话，再给必要数值/时间/图/依据和最多3个相关动作。状态问不铺全套影像，原因问引用阈值与证据，影像问突出同pair/frame/region，进度问分别列工单/问题/事件。相同问题同数据保持相同事实，不随机编回答；不同任务共享事实但首结论/重点证据不同。每轮保留原问句、解析任务、对象与读取时刻供核对。
7. **失效与冲突**：换库清上下文与待选择请求，目标归档/删除说明失效；换点不沿用旧照片和视频。界面另选对象时更新当前选择，旧回答仍标当时对象，不把旧结论改成新点。并发提交用请求代次防旧结果覆盖新对象；取消/停止授权阻止后续准备，失败不自动重放写入。
